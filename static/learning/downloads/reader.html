Java＋AI 项目自学路线

2026-10-26 调整。用同一个设备运维工单平台，按 A 后端业务 → B 一个 AI 功能 → C 验证改进 推进。A 包含“最小业务闭环”和“必要工程能力”两个检查点；RAG、Agent 是之后按证据选择的升级，不是默认必做清单。

每周以成果为目标，周内有弹性，每天约 3 小时；不承诺 20 周掌握全部内容。文件名中的“第几周”保留为旧教材索引，时间与实施顺序以新版阶段日程为准。课后答案是局部参考，不能把生成的代码视为已学会。

2026-10-31：已跟练 Spring Bean 配置与构造器注入，Web 复用 TicketService 和文件仓库，完成详情、列表、关键词查询与 POST 创建。课堂助手 GET 验证 200/400/404；学习者提供创建 201 截图，并反馈空白标题失败且数量不变。DTO、RequestBody、JSON 转换和异常 cause 经讲解；独立追踪仍需巩固。MyBatis/MySQL 业务、权限及 AI 尚未接入。

第一版只做这些

报修人选择启用设备并填写报修 → 管理员派给启用工程师 → 该工程师提交处理说明 → 原报修人验收关闭；能查自己的列表和详情，管理员看全部。由 Java 判断角色、归属、状态、版本和字段；MySQL 持久化并提供约束。最小同源页面或 HTTP 客户端足以演示。

A2 补齐登录、校验、统一错误、事务、关键测试、可重复启动与一次排错后，即可进入 B。不先做评论、退回、附件、设备后台大全、缓存、消息队列、微服务或 Kubernetes。

B 只做已有工单摘要/分类建议：先授权读取已有工单，用户看完后审阅；模型不能直接改状态或派单。没有 API key、模型名称、可访问端点或预算时，先完成客户端契约和本地故障测试；结果标注“真实调用待配置”，不能用模拟响应声称 AI 验收通过。

每次学习的四件事

  1. 说清这条业务需求需要什么知识，先读对应一两个类或 SQL。
  2. 自己完成一个小修改；助手给提示、审阅或局部示例，不一次生成整套功能。
  3. 运行一个正常场景和一个有价值的失败场景，记录预期与实际；已掌握的同质练习可跳过。
  4. 关掉答案解释输入、调用链、数据库变化和失败路径，再做一个变体。

AI 辅助编程记录“工具帮了什么、我怎样确认”；项目 AI 记录“模型请求、结构化输出、失败降级、质量和成本”。两者不混为同一能力。

离线阅读与准备

可打开连续阅读版，或下载完整自学包后解压，用浏览器打开 reader.html；包内Markdown可以独立阅读与记录。公开下载内容随课程同步更新，实际学习进度见时间线。

首次准备工具和依赖仍需网络；B阶段的真实模型调用需可用提供方、凭据与调用预算。未配置时可继续后端和本地契约测试，但明确记录“真实模型验证未完成”。遇到卡点先缩小为一条SQL、一个方法或一个请求，再查排错手册；按可投入时间调整选修范围。

首版建议的使用边界

B首版只展示/复制参考，不提供直接回写按钮。现有rename只在控制台，不能视为已有HTTP修改接口；以后若加入人工采纳改标题，须单独定义报修人归属、允许状态、expectedVersion和日志同事务的HTTP接口，再实施并验收。

设备运维工单平台项目说明

本页说明项目路线；当前实现与验收请配合项目文档阅读。计划中的能力不代表已经实现或掌握。

更新：2026-10-26。沿用既有 ops-ticket / JavaProject，在同一个设备运维工单主题中学习Java后端与AI应用开发。项目使用虚构设备资料，不依赖硬件接入；以开发、测试与交付能力为重点。

现有成果与实际起点

当前是 Java 21＋Maven 的本地控制台项目，保留内存/文件仓库、菜单、17项JUnit和可运行JAR。2026-10-28环境已升级为MySQL8.4.13、Connector/J26.10.0；独立JdbcTicketQueryDemo已查询真实工单，支持状态参数、SQL NULL和方法提取。正式业务仓库未接数据库，Java更新事务、HTTP、登录权限、完整处理验收及AI/Agent仍待实现。

现有 Java 结构不算复杂，可继续用。需要改的是后续范围：旧计划把六表、评论、退回、看板及众多扩展排在 AI 前，现在将首版收敛为核心业务和必需工程能力，随即接入一个可评估的 AI 功能。

已有源码/运行结果不等于学习者独立掌握。SQL关联筛选、统计/分页、提交回滚和双连接版本竞争已有反馈；JDBC查询与方法提取是跟写、经解释修改后运行成功。助手执行的环境迁移与临时验证不计作学习者独立能力；以学习时间线和项目验收为准。

同一个项目的三个主阶段

阶段 交付范围 验收之后再做什么
A1 最小后端业务 Java＋Spring Boot＋MyBatis＋MySQL，报修创建→派单→解决→验收关闭，详情/必要筛选 核心数据能持久化，能解释请求链；仍在本机教学
A2 基础工程 会话认证、三角色与归属权限、参数与异常、事务日志、重复/并发请求、关键测试、部署排错 小版本可运行可部署，能独立改一项业务后进入 B
B 一个真实 AI 功能 结构化工单摘要、分类建议和待补充信息，用户决定是否采用 API/结构校验/超时与错误降级可运行，真实调用有证据，进入 C
C 验证与改进 固定案例、无 AI 基线、内容质量、失败、延迟、用量和成本，改进后复验 用结果判断是否补 RAG、受控 Agent 或其他缺口

A1/A2 合在“Java 后端业务”主阶段中，分别对应最小业务与基础工程；评估从 B 首次调用就开始，C 专门整理并改进。Agent 不是必须从头做的第四个项目。按可检查的门槛推进，不承诺几周掌握；原 20 周文件名保留为教材索引。

第一版业务边界

设备来自虚构园区/实验室记录，无真实硬件连接。只保留三种角色：

角色 首版职责 不可越过的边界
REPORTER 报修人 选启用设备、创建、查自己的工单、验收 不能冒充别人报修、查询别人记录或自行派单
ENGINEER 工程师 查分给自己的工单、提交非空处理说明 不能处理别人名下工单或代报修人验收
ADMIN 管理员 查询、给 OPEN 工单指定启用工程师 不能随意设置状态或代报修人验收

流程为 OPEN→IN_PROGRESS→RESOLVED→CLOSED。首版不做验收退回、评论、公开注册、全套设备/用户后台、统计大屏。演示先用接口工具，随后可加简洁页面；不要求先学大型前端框架。

现有三表保留，A 阶段再加 ticket_action_log；处理说明存 resolve 动作 note，状态与日志同事务。暂不建 ticket_comment/ticket_resolution。创建重试用请求键，状态操作用前置状态＋期望版本；SQL 中 version 字段存在并不代表这些保护已实现。

具体规则、接口与验收不在本页重复维护，以项目 需求、设计、验收 为准。

第一项 AI 功能为什么这样选

工单经常只有杂乱描述。已有 title/description 就能支持“整理现象、给分类建议、指出缺的信息”，无需先做知识库或购置硬件。第一版对有权读取的工单返回 summary、category、missingInformation；category 限定 DISPLAY/PRINTING/HVAC/OTHER/UNKNOWN，只作为建议，不自动入库派单。首版只展示/复制参考，不直接写回标题。当前 rename 只有控制台和 Service 实现；以后要做人工采纳入口，先补明确权限、状态、版本和日志规则的 HTTP 接口。

这项功能能够练习真正的模型请求、响应结构、输入边界、成本和失败处理。AI 无依据时不编造型号/维修结论；模型不可用时正常报修、派单和验收继续运行。第一版不能声称故障诊断专家或自主维修 Agent。

B 开始前再选择供应商、模型与费用上限，准备本地环境变量；当前未配置或真实验证任何模型。Java 先实现清晰的 ModelClient 边界，调用 API，不强行拆 Python 服务。模拟响应只能验证解析与降级，不能充当真实模型效果。

RAG 和 Agent 的加入条件

  • 只有出现“需要根据手册给出处”的问题，才增加授权资料导入、来源版本、检索与引用；无相关依据时说明没有查到，记录召回和生成两种失败。
  • 只有需要自然语言查询本人/授权范围内工单，才增加受控只读工具。工具复用 Service，程序校验权限和参数，不让模型拼任意 SQL。
  • 只读工具稳定并有多步骤需求后，才加有限调用次数、上下文和失败处理。写入工具必须展示具体动作供确认，执行时重新检查权限/版本/参数，不能绕过 Java 业务规则。
  • 不把 Redis、MQ、微服务、Kubernetes、MCP、多 Agent、本地训练或大规模向量库作为 AI 的先修课。

技术与学习方式

沿用 Java 21、Maven；当前MySQL8.4.13与Connector/J26.10.0已经过独立恢复和连接验证。先补短JDBC更新/回滚实验，再接Spring Boot＋MyBatis，不重复升级现有环境。框架版本到接入时按官方兼容表固定；认证仍优先Spring Security＋Session Cookie，保留CSRF并使用框架密码编码器。

两种 AI 学习分开：AI 辅助编程可用于解释/评审/排错，但每个模块要自己读调用链、独立改需求并验证；产品内 AI 功能则必须自己接入、测试真实 API 和失败路径。安排少量高价值测试，避免重复抄同类断言；数据库事务必须用真实 MySQL 验证，不能只看 Mock。

每次约 3 小时是时间预算，不是作业定额：先回忆已有代码，再讲一个新概念、独立写一个小变更、验证并记录帮助和困难。每个阶段至少独立实现/修改一个功能、解释一次设计、排查一个故障。完整任务见 阶段学习计划。

求职匹配与信息边界

后端能力仍是 AI 应用的基础，不能从技术热度判断“纯后端已落后”。2026-10-26 核查的海康 Java 实习岗位仍覆盖 Java、Spring、MyBatis、SQL、测试与部署；质量管理软件实习也要求后端框架和 SQL，并提 AI 辅助开发。大华 AI 应用开发岗位可作 Java/AI 工程能力参照，但该岗位明确限定 2027 届，申请时须核对自己的毕业届别；详情信息来自官网搜索索引。

上述不是 2027 暑期岗位保证。每次投递核对本科门槛、毕业届别、杭州地点、每周出勤与连续实习时长。简历分别写已实现业务、真实 AI 验证、个人独立贡献和限制；没有测出的性能/成本不能编造。第二个项目等第一项目完成及岗位缺口明确后再决定。

工单表示什么

例如“教室投影仪无法开机”是一条报修。以后它会经历报修、派单、处理、验收。今天的 Ticket 只保存两个信息：id 是工单编号，title 是问题标题。

先理解： 认证回答“你是谁”，授权回答“你能做什么”。Session把登录身份留在服务器，浏览器持有会话Cookie；它不是把密码反复传给每个接口。密码哈希由框架编码器生成并匹配，不能通过每次重新encode后直接比较字符串。CSRF令牌帮助服务端验证修改请求的来源意图，它与登录身份是两回事。

  5. 浏览器验收与复盘，约4小时。 用普通窗口和无痕窗口建立两个独立会话。记录登录前后Cookie与/api/me变化、错误密码、停用账号、退出后再次查询以及缺失CSRF的结果。

SELECT id, title, status, created_at
FROM ticket

  • 你能解释关键代码，并独立完成一个小修改。
  • 简历只写已经实现的内容，所有成果有自己的代码或证据。

如果到 3 月仍差一两项，先筛选岗位、写简历和补缺；不能声称功能已经完成。把最近两周的时间集中到可投递版本，不继续扩展技术栈。已明确开放、条件匹配且截止较早的机会，可按实际完成情况如实申请。

每周时间怎么分

普通申请周参考 18 小时：岗位核对与定向投递 4 小时，基础与算法 5 小时，项目补缺 4 小时，模拟或正式面试 3 小时，反馈整理 2 小时。正式面试多时，替换模拟与部分项目时间，不要求在原计划上额外加班。

考试周可以缩成 6—9 小时：处理已有面试与重要通知、保留一次基础复习、完成一个小修复。暂停扩展，次周顺延。没有回复的一周也要按计划练习和检查岗位匹配，不能把每天刷新消息当成学习任务。

投递数量按机会质量调整，刚开始每周选择约 3—5 个确认匹配的岗位，之后根据实际岗位数量和反馈增减。这个数量只是个人起步参考，不是必须完成的指标，更不代表投得越多越容易录用。

筛一个岗位的固定步骤

先核对门槛，再判断能力匹配。岗位是否接受自己的毕业届别，比标题是否带“实习”更关键；限定其他届别的校招岗位不能直接当作当前可投机会。

  1. 来源与状态： 优先找企业官方招聘页面、官方发布渠道或学校核验过的信息，保存职位链接与查阅日期，确认仍能申请。
  2. 届别与身份： 是否明确接受本人毕业届别、在校本科生或无届别限制的日常实习；模糊时在实际申请沟通中如实说明毕业时间。
  3. 到岗条件： 地点、最早到岗、每周天数、连续月数，逐项与你能做到的范围比较。
  4. 技术要求： 标出必须项和加分项，将Java、Spring、MyBatis、MySQL、测试部署等与你的实际证据对应。
  5. 职责内容： 是否真正包含开发、联调、排错、测试或交付；了解有人指导、代码审阅和可承担任务的情况。
  6. 申请方式： 按正式渠道提交相应材料，保存职位编号和版本；不因为焦虑就夸大能力或隐瞒出勤限制。

为防止耗时失控，第一次核对单个岗位先控制在约15分钟。明显届别不符就标为不匹配，不花一晚准备。条件匹配的重点岗位，再花30—60分钟读业务、整理问题和调整简历描述。

独立学习与排错方法

每遇到问题，先把它变成可复现的小问题：写出输入、预期、实际、错误堆栈和最近改动。先读最靠近原因的异常，再检查配置与代码路径。查资料时带上框架版本和错误关键句，优先阅读对应官方文档；不要遇到一个报错就换一套技术栈。

如果30—45分钟仍无进展：把问题缩到最小示例，暂时回到最后能工作的提交，记录已经排除的原因。可以请同学、老师或技术社区帮助，并提供最小代码与完整错误信息；分享前移除密码和个人信息。当天仍可以完成不依赖该阻塞的复习、SQL练习或文档任务。

第 1 周答案

题 1：为什么构造器也要校验？ 创建对象也是输入数据的入口。如果构造器直接保存空标题，非法对象在第一次调用 rename 前已经存在。构造和修改应共用校验规则，保证任何正常完成的创建或修改都留下合法状态。

题 2：两个变量指向同一对象会怎样？ Ticket b = a 复制引用，没有复制对象。通过 b.rename("新标题") 修改同一个对象后，a.getTitle() 也返回“新标题”。只有再次 new Ticket(...) 才创建另一张对象。

题 3：为什么不用 static 字段？ static 字段属于类，所有实例共享。如果标题是 static，改第一张可能让第二张读取相同的新标题。每张工单自己的数据必须是实例字段。main 是 static，是因为程序入口不需要先创建 Demo 对象。

关键校验可以这样写在 Ticket 类内部。这里的 normalizeTitle 是私有静态工具方法：它只处理参数，不访问任何一张工单的字段，因此与“把 title 字段变成 static”不同。

private long id;
private String title;

public Ticket(long id, String title) {
    if (id <= 0) {
        throw new IllegalArgumentException("编号必须大于0");
    }
    String validTitle = normalizeTitle(title);
    this.id = id;
    this.title = validTitle;
}

private static String normalizeTitle(String value) {
    if (value == null) {
        throw new IllegalArgumentException("标题不能为空");
    }
    String normalized = value.trim();
    if (normalized.isEmpty() || normalized.length() > 50) {
        throw new IllegalArgumentException("标题长度必须为1至50");
    }
    return normalized;
}

public void rename(String newTitle) {
    this.title = normalizeTitle(newTitle);
}

先算赋值右边：校验抛异常时，赋值还没有发生，旧标题保留。getter 由你补上。不要先 this.title = newTitle 再判断，否则异常发生后对象已经被非法输入污染。

第 2 周答案

题 1：重复 Map.put 会怎样？ 相同键的新值会替换旧值。创建时应先检查 containsKey(id) 并拒绝重复，或使用 putIfAbsent 检查返回值。本阶段是单线程，先检查再放入足够；并发时不能直接推广这个结论。

题 2：为什么不从 1 开始？ 文件里已经有旧编号，重新从 1 开始可能覆盖或与旧记录冲突。读取全部记录后，空集合用 1，否则用现有最大 id 加 1。这仅用于单进程练习；数据库阶段改成 AUTO_INCREMENT，后期并发不能用 MAX(id)+1。

第 3 周答案

题 1：为什么不在业务方法里不断 new 文件仓库？ 这样业务被具体存储绑住，每次还可能重复加载或得到不同的内存状态。将 Repository 通过构造器传入，业务只调用约定接口，同一个对象的依赖清晰，也方便用内存实现做练习。

题 2：换存储时什么变、什么不变？ 启动组装位置改实现，Repository 实现内部改变；标题规范、允许的状态迁移、用户看到的成功或失败含义应保留。若一个实现允许重复编号，另一个拒绝，就没有遵守统一约定。

public class TicketService {
    private final TicketRepository repository;

    public TicketService(TicketRepository repository) {
        this.repository = java.util.Objects.requireNonNull(repository);

    public void rename(long id, String title) {

第 4 周答案

题 1：为什么不用 = NULL？ NULL 表示缺失或未知值，与它用普通等号比较得不到“相等为真”。筛选缺失值用 IS NULL，有值用 IS NOT NULL。SQL NULL 不等于字符串 'NULL'，也不等于数字 0。

题 2：改设备名为什么不用改工单编号？ 工单保存稳定的 device_id，关联时读取设备当前名称。同一设备改名仍是同一设备，id 不变。若未来有“保留报修当时名称”的业务需求，再专门设计快照字段。

题 3：外键能否保证处理人是工程师？ 不能。外键仅保证编号引用的用户存在；角色和启用状态还需 Service 校验。用户 1 即使存在，也只是 REPORTER。

  description VARCHAR(2000) NOT NULL DEFAULT '',
  device_id BIGINT NOT NULL,
  reporter_id BIGINT NOT NULL,
  assignee_id BIGINT NULL,

第 5 周答案

题 1：INNER JOIN 处理人为什么丢行？ 未派单工单的 assignee_id 是 NULL，没有匹配用户。INNER JOIN 只保留匹配成功的行，因此 101、103 被过滤掉。LEFT JOIN 保留工单，处理人相关列为 NULL。

题 2：为什么不 COUNT(*)？ 打印机没有工单，LEFT JOIN 仍保留一行，COUNT(*) 得到 1；COUNT(t.id) 只数非空工单编号，得到 0。统计前还要检查其他关联是否把工单复制成多行。

题 3：失败后为什么显式回滚？ 某条 SQL 失败通常不代表前面所有成功语句都已回滚；仍可能保留在未提交事务里。业务要求全成功或全失败时，异常路径主动 ROLLBACK，正常路径才 COMMIT，并释放连接。不要在失败后继续提交部分结果。

第 6 周答案

题 1：为什么不拼标题到 SQL？ 标题可能包含单引号等字符，拼接会改变 SQL 结构或制造注入风险。固定语句使用占位符绑定值，让输入作为数据处理。参数绑定不替代标题业务校验，也不能自动保证权限。

题 2：为什么退出后数据库数据还在？ 已提交数据由数据库持久化管理，不只存在 Java 进程内存中。Map 只在进程内；第 2 周能恢复是因为额外写了文件。不要把 commit 与 Java 对象仍在混为一谈。

题 3：200 和 JSON 是否够了？ 还要核对响应内容、id、字段、当前身份与可见范围是否符合请求。200 只表达服务端报告成功，不自动证明业务实现正确；比如错误返回了另一张工单也仍可能带 200。

static long insertTicket(String normalizedTitle, String description,
        long deviceId, long reporterId) throws SQLException {
    String sql = "INSERT INTO ticket "
        + "(title,description,device_id,reporter_id,status,version) "
        + "VALUES (?,?,?,?, 'OPEN',0)";
    try (Connection connection = openConnection();
         PreparedStatement statement = connection.prepareStatement(
             sql, Statement.RETURN_GENERATED_KEYS)) {
        statement.setString(1, normalizedTitle);
        statement.setString(2, description);
        statement.setLong(3, deviceId);
        statement.setLong(4, reporterId);
        if (statement.executeUpdate() != 1) {
            throw new SQLException("创建工单受影响行数不是1");
        }
        try (ResultSet keys = statement.getGeneratedKeys()) {
            if (!keys.next()) {
                throw new SQLException("没有取得生成的工单编号");
            }
            return keys.getLong(1);
        }
    }
}

此单语句演示使用新 JDBC 连接默认的自动提交。插入已提交却在读取生成键时异常，不应简单认为数据库一定没有新增；先按实际数据库状态排查，不要盲目重复提交。多步业务在第 9 周显式放入事务。数据库自增编号可能有空洞，不把它当连续计数器。

第7周答案和最小接口

7.1 创建请求为何不直接用数据库实体？ 数据库实体含id、reporterId、assigneeId、status、version等服务端字段，客户端没有修改它们的权利。专门的DTO只接收本次操作允许传入的字段，Service再构造合法对象。即便JSON附带 status=CLOSED，也不能把它复制成最终状态；可拒绝未知字段或忽略未知字段，业务结果都不能被它改变。

7.2 手动new与构造器注入的区别？ 手动new本身没有错，第3周就是这样组装对象的。但在Controller里到处new，会把业务和存储实现选择散落到多个入口，且自己new的Service通常不受Spring事务代理管理。构造器注入让对象依赖显式可见，由容器统一组装，也便于测试时传入替身。它不会自动让业务逻辑正确。

7.3 404、400、500分别先查什么？ 404先核对URL、HTTP方法、Controller映射以及资源编号；400先看JSON格式、字段类型、约束和请求Content-Type；500先看服务器异常堆栈与导致失败的数据库或业务调用。连接被拒绝甚至没有HTTP响应时，应先查进程和端口，不能归类为500。

第8周答案和Mapper

8.1 #{}与${}的区别？ #{title}把内容作为绑定参数，单引号只是内容；${title}先把文本拼入SQL，改变SQL结构的风险由此产生。值用 #{}。列名和排序方向不能当普通值绑定，应在服务端白名单中选择固定SQL，本项目直接固定排序即可。

8.2 reporterId为什么为null？ 先查SELECT是否选出 reporter_id且源数据非null；再查列名到属性名的映射或别名；最后查Java属性名、setter、类型是否一致。不是每个null都意味着数据库没数据。assigneeId初始允许null，应使用 Long，避免把“尚未派单”和编号0混在一起。

8.3 接口为何能注入？ MyBatis与Spring集成会扫描标记的Mapper，为接口生成代理对象，方法调用由代理定位映射SQL并执行。你不必手写实现类，但必须保证映射名、参数名、SQL和结果类型一致。具体扫描方式参见MyBatis Starter说明。

第9周答案和事务边界

9.1 为什么不能吞异常？ 事务方法如果捕获运行时异常后正常返回，框架可能把它视为一次成功调用并提交已做的修改。应让异常越过事务方法，由外层异常处理映射为HTTP错误；或明确标记回滚，但初学阶段采用前一种。不要 catch(Exception) 后只打印一行并返回false。

9.2 this.assign有什么问题？ Spring常通过代理在方法前后开始和结束事务。同一个对象内部直接调用自己，绕过外部代理，注解可能不生效。把事务边界放在Controller通过注入对象调用的公开Service方法上；不要new这个Service，不把事务写在只会内部调用的小工具方法上。Spring事务代理说明

9.3 为什么0行不能继续记成功日志？ WHERE条件未匹配意味着工单已变更、状态不对或不存在。没有成功修改，就没有派单成功这一业务事实。先区分不存在404、无权403，再把状态或版本不匹配作为409；抛异常使本次事务不产生成功记录。

第10周答案和分页校验

10.1 @Size能否拒绝空标题？ 不能单独完成。@Size(max=50)允许长度0，也通常把null视为有效；用 @NotBlank拒绝null、空字符串与纯空白，再加 @Size(max=50)限制上限。必须有Validation依赖并触发校验。

10.2 count漏条件会怎样？ items可能只有2条符合条件的工单，total却显示12，于是页面出现多余页码；接入权限后还可能泄露别人的工单数量。列表与count复用相同WHERE条件，仅排序与LIMIT有所不同。

10.3 为什么不能所有错误都200？ 浏览器请求工具、监控和调用方都依赖状态码区分成功与失败。200会使失败看起来像成功，页面可能清空用户输入或刷新列表，排错也更困难。状态码负责大类，code/message负责具体含义。

第11周答案和页面请求

11.1 fetch为何没有因500抛异常？ fetch主要用拒绝Promise表示网络等请求失败；拿到HTTP500响应仍属于收到了响应。代码必须主动看 response.ok 或 response.status。Fetch用法

11.2 评论为什么用textContent？ textContent把 <b> 当普通文字；innerHTML让浏览器把它解释成HTML，用户输入可能改变页面甚至执行不应执行的内容。本项目评论就是纯文本，直接用textContent最符合需求。

11.3 隐藏按钮能否保护接口？ 不能。用户能用HTTP客户端发送相同请求，甚至编辑浏览器里的页面。按钮控制只为了让人不误操作，服务端仍要验证身份、角色、归属、状态与版本。

以下是第11周app.js的局部辅助函数，供未接登录时使用；第12周应由后文带CSRF的函数替代。

async function requestJson(url, method = "GET", data) {
  const headers = { Accept: "application/json" };
  const options = { method, headers, credentials: "same-origin" };
  if (data !== undefined) {
    headers["Content-Type"] = "application/json";
    options.body = JSON.stringify(data);
  }
  const response = await fetch(url, options);
  const text = await response.text();
  let result = null;
  if (text) {
    try { result = JSON.parse(text); }
    catch { throw new Error("服务器返回格式异常，请检查Network响应"); }
  }
  if (!response.ok) {
    throw new Error(result?.message ?? `请求失败：${response.status}`);
  }
  return result;
}

先读文本并判断是否为空，因而204不会直接执行 response.json()。页面事件处理应 try/catch/finally：try发请求并更新页面，catch展示消息，finally恢复按钮。禁用按钮能降低双击概率，但仍须保留后端条件更新。

第12周答案和Session登录接线

12.1 authenticate成功为何不代表下一次也登录？ authenticate只完成本次凭据验证并返回认证对象。认证上下文还必须通过框架机制保存，下次请求才能从会话恢复。主线使用框架formLogin，由过滤器执行认证、会话处理和上下文保存；不要自写仅调用AuthenticationManager的“假登录成功”接口。认证持久化

12.2 正确密码却403先查什么？ 查看请求是否包含当前会话对应的CSRF头，Cookie是否随请求发送，登录参数是否用表单编码而非JSON。缺少CSRF可能在验证密码之前被拒绝，所以改密码、删除Security依赖都不是对应修复。

12.3 登录后旧CSRF为何失效？ 框架会在成功登录和退出时清除旧令牌；浏览器应重新GET /api/csrf并使用新的返回值。这也是为什么不能把令牌永久写死在JavaScript中。CSRF令牌生命周期

账号读取的连接点

前置：编写 AppUserRow普通JavaBean，属性为id、username、passwordHash、role、enabled；enabled用boolean并提供 isEnabled()。AppUserMapper.findByUsername采用 #{username}，返回用户行或null：

SELECT id, username, password_hash, role, enabled
FROM app_user
WHERE username = ?;

这里的问号表示绑定参数；MyBatis实际映射写 #{username}。username有唯一约束。下面是放入配置类的局部Bean方法，需要导入你自己的Mapper，以及框架的Bean、UserDetailsService、UsernameNotFoundException、User：

@Bean
UserDetailsService userDetailsService(AppUserMapper users) {
    return username -> {
        AppUserRow row = users.findByUsername(username);
        if (row == null) {
            throw new UsernameNotFoundException("账号或密码错误");
        }
        return User.withUsername(row.getUsername())
                .password(row.getPasswordHash())
                .roles(row.getRole())
                .disabled(!row.isEnabled())
                .build();
    };
}

Security配置模板

这是一个完整配置类模板，前提是已加入Security依赖、上面的UserDetailsService Bean已由另一个配置类提供，并且登录页、CSRF端点及业务Controller存在。它只完成认证接线；第13周Service里的数据权限仍需自己写。若项目已有SecurityFilterChain，要修改现有配置，不叠加第二份不明顺序的配置。

package cn.wishbottle.opsticket.security;

import java.io.IOException;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.authentication.dao.DaoAuthenticationProvider;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.csrf.CsrfException;

@Configuration
public class SecurityConfig {
    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http, UserDetailsService users,
            PasswordEncoder passwords) throws Exception {
        var provider = new DaoAuthenticationProvider(users);
        provider.setPasswordEncoder(passwords);
        http.authenticationProvider(provider);
        http.csrf(Customizer.withDefaults());
        http.requestCache(cache -> cache.disable());
        http.authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/index.html", "/login.html",
                        "/app.js", "/auth.js", "/style.css", "/favicon.ico",
                        "/api/csrf", "/error").permitAll()
                .requestMatchers("/api/**").authenticated()
                .anyRequest().denyAll());
        http.formLogin(form -> form
                .loginPage("/login.html")
                .loginProcessingUrl("/api/login")
                .successHandler((request, response, auth) -> response.setStatus(204))
                .failureHandler((request, response, error) -> writeError(response, 401,
                        "{\"code\":\"LOGIN_FAILED\",\"message\":\"账号或密码错误\"}"))
                .permitAll());
        http.logout(logout -> logout
                .logoutUrl("/api/logout")
                .deleteCookies("JSESSIONID")
                .logoutSuccessHandler((request, response, auth) -> response.setStatus(204))
                .permitAll());
        http.exceptionHandling(errors -> errors
                .authenticationEntryPoint((request, response, error) ->
                        writeError(response, 401,
                                "{\"code\":\"UNAUTHENTICATED\",\"message\":\"请先登录\"}"))
                .accessDeniedHandler((request, response, error) -> {
                    String body = error instanceof CsrfException
                            ? "{\"code\":\"CSRF_INVALID\",\"message\":\"请求令牌失效，请刷新页面\"}"
                            : "{\"code\":\"FORBIDDEN\",\"message\":\"没有操作权限\"}";
                    writeError(response, 403, body);
                }));
        return http.build();
    }

    private static void writeError(HttpServletResponse response, int status,
                                   String fixedJson) throws IOException {
        response.setStatus(status);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write(fixedJson);
    }
}

该例只写固定JSON常量，没有拼接用户内容；动态对象应交给JSON序列化器。Boot4的JSON包与旧教程可能不同，不为一个错误响应照搬旧ObjectMapper依赖。DaoAuthenticationProvider(UserDetailsService)构造器及 setPasswordEncoder已按当前API核对。认证提供器API

框架处理POST /api/login与POST /api/logout，不要再为这两个地址写同名Controller。第13周如增加HTTP级角色匹配，应放在 /api/** 的宽泛规则前面；具体工单归属仍在Service检查。

CSRF端点模板

以下是完整Controller模板，继续使用默认会话CSRF存储，并通过参数取得框架已经处理的令牌，不自行替换令牌编码方式。

package cn.wishbottle.opsticket.controller;

import org.springframework.http.CacheControl;
import org.springframework.http.ResponseEntity;
import org.springframework.security.web.csrf.CsrfToken;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class CsrfController {
    public record TokenView(String headerName, String token) { }

    @GetMapping("/api/csrf")
    public ResponseEntity<TokenView> token(CsrfToken csrf) {
        var view = new TokenView(csrf.getHeaderName(), csrf.getToken());
        return ResponseEntity.ok().cacheControl(CacheControl.noStore()).body(view);
    }
}

let csrfInfo;

async function readResponse(response) {
  const text = await response.text();
  let data = null;
  if (text) {
    try { data = JSON.parse(text); }
    catch { throw new Error(`响应格式异常：${response.status}`); }
  }
  if (!response.ok) {
    const error = new Error(data?.message ?? `请求失败：${response.status}`);
    error.status = response.status;
    error.code = data?.code;
    throw error;
  }
  return data;
}

async function refreshCsrf() {
  const response = await fetch("/api/csrf", {
    credentials: "same-origin", cache: "no-store"
  });
  csrfInfo = await readResponse(response);
}

async function login(username, password) {
  await refreshCsrf();
  const response = await fetch("/api/login", {
    method: "POST",
    credentials: "same-origin",
    headers: { [csrfInfo.headerName]: csrfInfo.token },
    body: new URLSearchParams({ username, password })
  });
  await readResponse(response);
  await refreshCsrf();
}

async function apiJson(url, method = "GET", data) {
  const headers = { Accept: "application/json" };
  const options = { method, credentials: "same-origin", headers };
  const modifies = !["GET", "HEAD", "OPTIONS"].includes(method.toUpperCase());
  if (modifies) {
    if (!csrfInfo) await refreshCsrf();
    headers[csrfInfo.headerName] = csrfInfo.token;
  }
  if (data !== undefined) {
    headers["Content-Type"] = "application/json";
    options.body = JSON.stringify(data);
  }
  return readResponse(await fetch(url, options));
}

async function logout() {
  await apiJson("/api/logout", "POST");
  csrfInfo = undefined;
  await refreshCsrf();
}

登录成功后可跳回主页；新页面重新调用refreshCsrf即可。页面遇401提示重新登录；遇403区分 CSRF_INVALID 与业务无权；遇409提示数据已变更。不要对失败POST无限自动重发，避免重复创建和评论。CORS不在本阶段引入，也不添加允许任意来源携带凭据的配置。

第14周 并发与事务

14.1 先查询再无条件更新为什么出错

因为查询到的是某个时刻的结果，不是对未来修改的独占许可。下面是可能发生的顺序：

顺序 管理员请求 A 管理员请求 B
1 查询到 OPEN、version=0
2 也查询到 OPEN、version=0
3 派给工程师甲并更新
4 无条件派给工程师乙，覆盖 A 的结果

if (ticket.getStatus() == OPEN) 只检查 Java 对象中那份旧值。修复要让数据库在实际修改时再次检查状态和期望版本：

UPDATE ticket
SET assignee_id = ?, status = 'IN_PROGRESS',
    version = version + 1, updated_at = CURRENT_TIMESTAMP
WHERE id = ? AND status = 'OPEN' AND version = ?;

三个 ? 分别绑定处理人、工单编号、用户本次操作基于的版本。MyBatis 可改为命名参数，不能拼接用户输入到 SQL。只有返回影响行数 1 才代表修改成功。

可以先在两个 MySQL 客户端窗口验证。准备一张新的 OPEN 测试工单并记住编号与版本；A 开始事务后执行条件更新但暂不提交；B 开始事务并对同一旧版本执行条件更新，通常会等待；A 提交后 B 继续，条件已不满足，影响行数为 0。B 回滚结束实验。每次 UPDATE 后立即看客户端影响行数或执行 SELECT ROW_COUNT()。此实验直接操作数据库，只验证并发更新机制；应用权限和日志事务还要通过应用接口验证。

14.2 有事务为什么还要条件更新

事务用于让“修改工单、写日志”等操作形成一个整体；它不会自动替你决定“两位管理员谁的派单有效”。若 SQL 只按 id 更新，后来的事务仍可能在前者提交后覆盖处理人。条件更新把业务前提写进同一条 SQL，避免检查和修改之间的空隙。

版本号还能表达“你操作的是旧页面中的工单”。对 OPEN 派单来说状态条件已经能阻止第二次派单，保留版本条件则让后续其他修改也能沿用一致的冲突约定。本项目并不要求为此引入分布式锁。

局部 Service 结构如下，类名和调用方法需要对应自己的实现：

@Transactional
public void assign(long ticketId, long engineerId, long expectedVersion,
                   CurrentUser actor) {
    requireAdmin(actor);
    requireEnabledEngineer(engineerId);
    requireTicketExists(ticketId);
    int changed = ticketMapper.assignIfOpen(
            ticketId, engineerId, expectedVersion);
    if (changed != 1) {
        throw new ConflictException("工单已变化，请刷新后重试");
    }
    actionLogMapper.insertAssign(ticketId, actor.id(), engineerId);
}

CurrentUser、校验方法和 ConflictException 都是项目自己的类型或方法；ConflictException 可继承 RuntimeException。把它映射为 409。此处 actor 必须从服务器认证上下文取得，不能由客户端提交一个管理员编号冒充。状态和日志由同一个事务管理器管理、使用同一数据源参与事务。Spring 声明式事务

14.3 日志写失败后数据库应是什么样

整个业务事务应回滚：工单保持原状态、原处理人和原版本，没有这次派单日志。如果初始值为 OPEN、assignee_id 为 NULL、version 为 0，失败后仍应是这些值。

默认声明式事务对未被吞掉的运行时异常进行回滚；如果是检查型异常，要明确配置适当的回滚规则。不要捕获异常后只打印一句话、继续正常返回；不要让日志写入进入单独提交的事务。事务入口应由另一个组件调用 Spring 管理的 Service Bean，而不是 new Service()，也不是在同一个类内部依赖自调用来启动事务。

诊断顺序： 先确认调用的是 Spring Bean；再看异常是否逃离事务方法；再看两个 Mapper 是否用同一数据源；最后检查日志方法是否另开事务、更新是否自动提交。不要仅凭注解存在就认定事务一定生效。

第15周 自动测试

15.1 mock 成功能否证明数据库事务正确

不能。mock 返回的是你预设的行为，没有真实执行 SQL，也没有数据库锁、约束和提交过程。它可以证明 Service 遇到 Mapper 返回 0 时抛出冲突，却不能证明两个真实事务竞争时最终只成功一个。

最小 JUnit 示例只说明断言用法，不与项目类名绑定：

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class TitleRuleTest {
    private String normalizeTitle(String title) {
        if (title == null || title.isBlank()) {
            throw new IllegalArgumentException("标题不能为空");
        }
        return title.strip();
    }

    @Test
    void blankTitleIsRejected() {
        assertThrows(IllegalArgumentException.class,
                () -> normalizeTitle("   "));
    }

    @Test
    void surroundingSpacesAreRemoved() {
        assertEquals("投影仪无法开机", normalizeTitle(" 投影仪无法开机 "));
    }
}

在正式项目中，应直接测实际领域方法或 Service，避免把业务规则复制到测试类再测复制品。上面只适合第一次学习 JUnit 时运行，之后删除重复规则，用真实实现替换。

数据库集成测试至少实际调用 MyBatis 和 MySQL：创建测试用户、设备与 OPEN 工单；调用真实 Service；重新查询 ticket 和 ticket_action_log；核对状态、版本和日志。并发测试需要两条独立事务路径，测试前数据必须已经提交，不能被外层未提交的准备事务挡住。对每个等待和 Future 设置超时，失败时也释放门闩并关闭线程池。

15.2 测试自动回滚为什么会掩盖业务错误

假设 Service 忘写事务，但测试方法自己开了事务。Service 的数据库操作可能加入测试事务，测试结束时一起被回滚，于是你误以为业务本来就会回滚。真实 HTTP 请求没有这个测试外壳，可能只完成了工单修改而没写日志。

验证步骤要让业务事务独立承担责任：

  1. 测试方法本身不加自动回滚事务；使用仅能访问 ops_ticket_test 的配置和账号。
  2. 创建并提交一张新的 OPEN 工单，记录初始值。
  3. 在测试配置中让“写操作记录”这一步抛出运行时异常，但工单 Mapper 和数据库连接仍真实工作。可以使用仅测试生效的日志写入组件，或对实际日志组件做故障注入；不替换工单 Mapper。
  4. 调用 Spring 管理的派单 Service，断言确实抛出了预期异常。
  5. 在业务调用结束后开启新的查询，核对工单与日志；不能只检查内存里的旧对象。
  6. 清理这项测试创建的记录，不清空整个库。

步骤 3 没有执行真实日志 SQL，也能检查真实工单更新是否被异常回滚；若要验证数据库约束引起的失败，可在测试专用日志写入路径中故意写入违反已有非空约束的值。两种方式都必须在测试环境隔离，不能加一个对外的“故障开关”接口。

可用下面的查询核对。:id 是说明中的参数占位符，实际通过 PreparedStatement、Mapper 参数或数据库客户端变量绑定，不能直接把这段冒号语法当普通 MySQL SQL 执行。

SELECT status, assignee_id, version FROM ticket WHERE id = :id;
SELECT COUNT(*) FROM ticket_action_log
WHERE ticket_id = :id AND action = 'ASSIGN';

真实端口的接口测试运行在服务端线程中，测试方法自动回滚不会自动覆盖服务器事务，因此数据清理也要单独安排。Spring Boot 应用测试

15.3 怎样确认 403 是权限拒绝

先分清请求：普通 GET 查询不要求 CSRF token，所以越权读取的 GET 测试主要确认已登录、账号角色正确、工单存在且属于另一个报修人。写入接口如 POST，需要同时提供有效登录身份和有效 CSRF token，再验证角色或资源权限。

例如使用 Spring Security 的 MockMvc 测试辅助时，局部示例为：

mockMvc.perform(post("/api/tickets/{id}/resolve", ticketId)
        .with(user(actualOtherEngineerPrincipal))
        .with(csrf())
        .contentType(MediaType.APPLICATION_JSON)
        .content("{\"content\":\"已更换线缆\",\"expectedVersion\":0}"))
    .andExpect(status().isForbidden());

actualOtherEngineerPrincipal 应是应用能识别用户编号的真实 UserDetails 实现，且是另一个 ENGINEER；只写 user("name").roles("ENGINEER") 可能没有项目需要的 id。测试预先创建状态为 IN_PROGRESS、版本为 0、分配给其他工程师的工单；请求按接口约定提供 content 和 expectedVersion，避免因请求字段错误先触发 400，无法检验权限。user 与 csrf 的静态方法来自 Spring Security Test 支持。CSRF 测试说明

再补一个对照：正确处理工程师、相同有效请求应成功。最后补缺少 CSRF token 被拒绝的独立用例。三个结果对应三条不同规则，不能混成一个用例。如果项目对不可见资源统一返回 404，就按既有接口契约断言 404，并检查不存在信息泄露，不要为了教材字面数字更改已经明确的策略。

本周诊断： 所有请求都 403 先看安全过滤链；只有部分身份失败再看数据权限；事务测试偶尔卡住先看准备数据是否提交、等待是否有超时；第二次跑失败先看测试主键或唯一用户名是否重复。

16.3 没有实验能不能写高并发高性能

不能把未测量的能力写成已证实的结果。可以写已经实现的具体行为，例如：

使用状态与版本条件更新防止重复派单；在真实 MySQL 上验证两个相同期望版本的请求只成功一次，并通过事务保持工单修改与操作记录一致。

这是功能和一致性描述，不等于系统吞吐量结论。做过性能实验以后，写明测试环境、数据量、请求方式和结果，避免省略上下文。没有真实公司用户，就写个人学习项目，不能写“服务数万用户”。

本周诊断： IDEA 能跑而 jar 不行，优先比较 JDK、配置和打包产物；只有自己的电脑能跑，核查绝对路径与环境变量；新终端缺少配置，检查变量是否只在旧终端或 IDE 生效。

第17周 部署与恢复

17.1 容器运行为什么不代表数据库可用

“容器进程存在”只是一个状态。MySQL 可能还在初始化，也可能因目录权限、密码、端口或数据版本不匹配而无法服务。应用可能把 localhost 错当成另一个容器的地址，或者数据库还没就绪就尝试连接。

排查顺序：

  1. docker compose ps 看容器状态与端口。
  2. docker compose logs --tail 100 db 看数据库服务日志，db 改成自己的服务名。
  3. 检查应用配置中的主机、端口、库名与账号；容器之间用数据库服务名和内部端口。
  4. 使用实际配置尝试连接，区别连接拒绝、认证失败和找不到数据库。
  5. 数据库可用后再看应用日志；必要时设置数据库健康检查与应用连接重试。

没有 Docker 时同样适用：先确认 MySQL 服务，再检查地址、认证、库表，最后查应用。不要反复重装所有工具来掩盖一个错误端口。

17.2 为什么还要实际恢复

文件可能为空、不完整、字符编码不正确，或依赖没有一起导出。你还可能没有恢复权限、选错目标库、漏掉关联数据。恢复测试让“有文件”变成“这份文件确实能重新形成可用数据”。

以下是按当前已实现表进行的恢复练习；新首版是用户、设备、工单、操作记录四张InnoDB表（当前学习库尚只有前三张），评论和独立处理记录表属于延后扩展，不覆盖已有库。示例假定备份由课程中不带 --databases 的命令生成，当前目录有 backups 子目录。

  1. 停止向学习数据写入，记下源库每张表记录数及两条含中文的工单；备份完成后先确认文件非空。
  2. 打开备份文本，确认没有 CREATE DATABASE、USE ops_ticket_dev 或其他切换到源库的语句。如果有，停止导入，回到课程备份命令重新生成，不要盲目改几个词继续。
  3. 使用有建库权限的本地管理账号创建一个全新库，示例 SQL 如下。若库已存在，换一个新名称；不要删除同名库。
CREATE DATABASE ops_ticket_restore_20270201
CHARACTER SET utf8mb4;
  1. 确认恢复账号只对这个恢复库有本次恢复所需权限。恢复 SQL 通常含建表和插入语句，可能包含 DROP TABLE IF EXISTS；因此目标必须是新空库，不能因为“名称看起来差不多”就复用旧库。
  2. 在项目根目录运行下面的交互式客户端命令，账号名替换为实际恢复账号：
mysql -u your_restore_user -p ops_ticket_restore_20270201
  1. 进入 mysql> 后，先核对当前库为空，再从当前终端工作目录导入：
SELECT DATABASE();
SHOW TABLES;
SOURCE backups/ops_ticket_dev_20270201.sql;
SHOW TABLES;

SOURCE 是 mysql 客户端命令，文件路径指客户端机器上的文件。相对路径不可用时，改用自己确认过的绝对路径与正斜杠；不要把 Linux 的 < file.sql 重定向直接复制到 Windows PowerShell。

  1. 比较当前已实现的 app_user、device、ticket、ticket_action_log 的行数；若以后实现评论和独立处理记录，再额外检查对应扩展表，检查中文标题、密码哈希和时间字段；用 JOIN 检查工单引用的用户和设备都存在。
  2. 用临时外部配置把本机应用连接到恢复库，执行一次查询和登录演示。结束后恢复原配置，保留验证记录，不要求删除恢复库。

例如检查恢复库中的工单关联是否缺失：

SELECT t.id
FROM ticket t
LEFT JOIN device d ON d.id = t.device_id
LEFT JOIN app_user u ON u.id = t.reporter_id
WHERE d.id IS NULL OR u.id IS NULL;

结果应为空，但空结果只说明这两种关联未发现缺失，不代表所有恢复验证都通过。备份文件包含学习账号的密码哈希，也应作为私有文件保存。MySQL 备份工具说明

17.3 停止容器与删除卷有什么区别

docker compose stop 停止运行，保留容器及持久化数据，之后可以再启动。数据库使用命名卷时，正常停止和启动不应使工单消失。删除承载 MySQL 数据的卷会删除其中数据，之后启动可能得到一个全新数据库。

不要用 docker compose down -v 演示“安全重启”；其中 -v 会删除 Compose 管理的相关卷。即使只执行不带 -v 的 down，也应事先知道数据到底存在命名卷、绑定目录还是容器可写层，不能凭命令名称判断数据一定保留。Docker Compose down

本周诊断： 重启数据丢失先查持久化位置；恢复乱码先查导出和客户端字符集；导入权限不足就核对恢复账号权限，不要改成面向所有库的高权限账号后忘记收回；备份看似成功仍要检查退出结果和文件内容。

第18周 索引线程池与 JVM

18.1 使用索引就一定更快吗

不一定。索引可能只排除很少数据，还需要大量回表；表很小时扫描全表反而更简单；排序、返回字段、统计信息和缓存状态也会影响结果。key 有值只说明选择了某个访问路径，不能代替实际测量。

本项目的候选索引把相等条件 reporter_id、status 放前面，再按查询排序设计时间和 id 列。它适合特定查询，不保证对“按设备统计”也有帮助。优化记录可使用下面的模板，数值必须自己测量：

数据量和分布：____条工单，OPEN约____%，指定报修人约____条
查询 SQL 和参数：____
环境与数据库版本：____
索引前执行计划及10次耗时：____
索引后执行计划及10次耗时：____
是否排除预热、是否相同返回结果：____
结论与局限：____

传统 EXPLAIN 的 rows 是估算；EXPLAIN ANALYZE 会执行支持的查询并提供实际执行信息，所以仅对自己理解成本的 SELECT 使用。没有明显差异时保留这个结论，同样体现测量能力。MySQL EXPLAIN

18.2 两线程两队列提交五项会怎样

在前两项任务都持续等待、尚未完成的前提下：任务 1、2 占用两个工作线程；任务 3、4 进入队列；任务 5 因线程与队列都满，被 AbortPolicy 拒绝并抛 RejectedExecutionException。

下面是一段独立 Java 21 实验，不接入工单业务。它使用门闩固定观察条件，不依赖“机器正好比较慢”。

import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class PoolDemo {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch release = new CountDownLatch(1);
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                2, 2, 0, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(2),
                new ThreadPoolExecutor.AbortPolicy());
        try {
            for (int i = 1; i <= 5; i++) {
                final int taskId = i;
                try {
                    pool.execute(() -> {
                        try {
                            release.await();
                            System.out.println("完成任务 " + taskId);
                        } catch (InterruptedException e) {
                            Thread.currentThread().interrupt();
                        }
                    });
                } catch (RejectedExecutionException e) {
                    System.out.println("被拒绝的任务 " + taskId);
                }
            }
        } finally {
            release.countDown();
            pool.shutdown();
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                pool.shutdownNow();
            }
        }
    }
}

预期第五项被拒绝，其余四项完成；四个完成信息之间的顺序不固定。这里使用 execute，若改成 submit 并在任务中抛异常，需要查看 Future.get() 的异常结果，不能只看提交方法有没有抛异常。线程池大小也必须考虑数据库连接和 CPU 等下游资源。Java 21 线程池文档

18.3 无限线程和永久 List 分别有什么风险

反复创建大量线程会增加线程栈、调度和系统资源开销，严重时无法再创建线程。把所有查询结果一直保存在某个长期存活的 List 中，会让这些对象仍可达，GC 无法回收，堆使用量持续增长。

GC 不是“内存不够时自动把没用的数据都猜出来删除”。程序还持有引用，GC 通常就必须认为对象可能被使用。数据库连接、文件等外部资源应按生命周期关闭，也不能等 GC 替你处理。应限制分页大小、缓存容量和线程数，并观察真实资源使用。

本周诊断： 索引没被选不代表索引创建失败，先看查询和数据分布；线程池程序一直不退出，先看任务是否结束、门闩是否放行、池是否关闭；内存升高不必立即调堆，先查是否无界集合或无界排队。

第19周 缓存与知识库

19.1 两个报修人能共用列表缓存吗

不能直接共用。列表结果受当前登录用户、角色、筛选条件和分页影响。若 A 的结果写入一个公共 key，B 读取它，就可能看见 A 的私有工单。鉴权也不能因为“有缓存”而跳过。

这也是本课程只推荐先缓存管理员统计的原因：范围比较明确，容易验证。若以后缓存私有列表，key 至少需要表达正确的用户与查询范围，例如下面只是结构示意：

ticket:list:reporter:1:status:OPEN:device:all:page:1:size:20

还需要考虑角色变更、数据变更和失效策略。包含用户 id 只是必要设计的一部分，并不自动让整个缓存方案安全正确。

19.2 数字滞后什么时候是约定行为

如果功能明确允许“最多 30 秒陈旧”，页面显示更新时间，缓存过期后能重新加载，那么 10 秒前的数据可能符合约定。如果已超过约定窗口仍不更新，或者把旧数据用于必须立即准确的派单判断，就是错误。

本项目派单是否合法必须由数据库条件更新决定，不能从统计缓存判断。缓存统计只辅助展示。测试至少包含以下步骤：查询并记录初始数量 → 创建一张工单 → 在约定窗口内读取 → 过期后再读取并核对数据库。若采用主动失效，还应检查每一种会改变状态数量的操作是否触发失效。

缓存服务不可用时可回退数据库，但也要观察请求量是否在本机能承受的范围。个人项目先保证正确性，不用为了一个统计查询立即搭建复杂集群。

19.3 没接模型的知识库有什么价值

它仍能把常见故障整理成可查询资料，减少重复查找；可以验证文章维护、检索、分页、输入处理和来源展示。比如输入“投影 黑屏”，返回两条含关键词的条目并说明匹配依据，找不到就明确显示无结果。

自测数据至少包括：命中一条、命中多条、没有匹配、空白输入、停用文章不展示。不要把关键词匹配叫成语义检索，也不要把简单数据库搜索写成 RAG。以后接模型时才考虑检索结果怎样进入上下文、引用怎样验证和无依据时怎样回答。

本周诊断： 先核对原始 SQL 结果，再看缓存；先核对关键词规则，再谈模型；扩展导致主线不稳定时回到最后通过测试的版本，保留扩展代码与问题记录。

第20周 面试与独立修改

20.1 一分钟解释防止重复派单

参考表达，必须用自己的实现替换细节：

两个管理员可能同时读到工单处于 OPEN，直接按 id 更新会产生覆盖。我把工单 id、OPEN 状态和页面读到的版本一起放进 UPDATE 条件，成功后版本加一，并检查影响行数。只有一个请求更新一行，另一个返回零行时转成 409，提醒刷新。工单修改和操作记录在同一个事务里。我用两个独立请求携带同一初始版本验证，最终只派单一次，版本只加一，日志只有一条。

追问“为什么不用 Java 锁”时说明 JVM 内锁的范围；追问“日志失败怎么办”时说明回滚验证；追问“版本能防止所有重复提交吗”时说明这是本次派单的状态与并发策略，不等于所有接口都自动幂等。

20.2 没压测怎样回答并发能力

如实回答范围：

目前做了并发正确性验证，两个请求竞争同一张工单只成功一个，但没有完成系统容量压测，所以我不能给出吞吐量上限。我做过的查询实验是……。如果要测容量，我会先固定机器、数据量、请求比例和并发模型，观察响应时间、错误率、CPU、数据库连接与慢查询，再逐步增加负载。

不要把“两个请求的并发冲突测试”说成“支持高并发”。不了解的指标可以说还没测，再解释已经验证的部分。

20.3 新增设备筛选要改什么

先确认接口参数如 deviceId 的含义和可选性，再沿请求路径检查：

  1. DTO 或请求参数接收设备编号；校验非法编号、分页大小等输入。
  2. Service 仍从登录身份确定可见范围。设备过滤只是增加条件，不能替代报修人或处理人限制。
  3. Mapper 的列表和总数查询都增加同样的设备条件，保持分页统计一致。
  4. 索引是否需要调整，用实际查询决定；没有测量就先保留简单实现。
  5. 增加接口测试，覆盖自己的设备工单、他人的同设备工单、无结果和不传参数；更新接口说明与页面。

报修人查询的核心意思应当是：

WHERE reporter_id = :currentUserId
  AND device_id = :deviceId

可选状态等条件继续用 AND 组合，不能误写成 reporter_id = ... OR device_id = ...，否则可能把同设备的他人工单泄露出来。这里的冒号仍是参数说明，MyBatis 实现时换成绑定参数。

用既有样本验证尤其直接：reporter_a 是用户 1，reporter_b 是用户 4；101 和 103 都关联设备 1，但报修人不同。用户 1 按设备 1 筛选时能看到 101，不应该因为设备相同就看到 103；管理员在合法权限下可以看见两者。

本周诊断： 讲不清就顺着一条真实请求解释；现场小改先画影响范围再动手；总数和列表不一致先查两个 SQL 条件；问题没做过就承认范围，不编测量结果。

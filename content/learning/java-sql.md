## 第 1 周 创建一个始终合法的工单对象

原参考日期（不作为截止时间）：2026 年 10 月 12 日至 18 日。前置：会写 `main`、变量、`if` 和方法调用；能说明 `private` 与成绩范围检查的区别。成果：运行 `TicketDemo`，创建两张工单、读取标题、修改标题，并证明非法输入不会破坏原对象。

| 任务 | 约用时 | 做到什么程度 |
| --- | --- | --- |
| A 写对象 | 3 小时 | 写 `private long id`、`private String title`、构造器和 getter；在 Demo 中创建编号 1、2 的对象，逐个打印 |
| B 加校验 | 3 小时 | 编号必须大于 0；标题先判断 `null`，再 `trim()`，处理后长度为 1 至 50。先校验再赋值 |
| C 修改标题 | 3 小时 | 加 `rename(String newTitle)`；构造与修改共用一个私有校验方法；不提供 `setId` |
| D 观察执行过程 | 3 小时 | 在构造器、校验方法和 `rename` 各设断点；观察 `this`、形参、字段；尝试让两个变量指向同一对象 |
| E 基础与保存 | 3 小时 | 用循环找整数数组最大值，验证空数组如何处理；在项目目录学习 `git status`、`git diff`、一次明确文件的提交 |
| F 独立验收 | 3 小时 | 合上答案重写标题校验；运行下面用例，记录一个错误及修复；回答三道自测 |

对象是某张工单，类是描述它有哪些数据和操作的代码。`this.title` 是当前对象的标题，参数 `title` 是调用者刚传进来的值。两者同名不代表它们自动关联。`private` 把直接修改入口收拢到类内部；入口中的校验才负责阻止非法数据。异常会中断当前正常执行路径；捕获后才能继续执行后面的演示用例。

标题长度本阶段按 Java `String.length()` 计算，验收先用普通汉字与英文字母；这不是“所有 Unicode 字符都占一个位置”的承诺。`trim()` 的规则也不要自行换成其他空白处理方式。先保持项目规则统一。

| 输入或操作 | 预期结果 |
| --- | --- |
| `new Ticket(1L, "  投影仪无法开机  ")` | 编号 1，标题为 `投影仪无法开机`，两端空格已去掉 |
| 标题为 `null`、`""`、`"   "` 或 51 个 `A` | 抛 `IllegalArgumentException`，该次创建不成功 |
| 标题为 1 个或 50 个 `A` | 创建成功 |
| 编号为 0 或 -1 | 抛 `IllegalArgumentException` |
| 合法工单调用 `rename(" ")` | 抛异常，原来的标题仍在 |
| 创建两张工单后只修改第一张 | 第二张标题不变 |

自测：①为什么构造器也要校验，不能只在 `rename` 校验？②`Ticket b = a; b.rename("新标题");` 后 `a` 的标题是什么，为什么？③为什么不能把 `id`、`title` 写成 `static`？

卡住提示：构造器与类同名，没有返回类型；读取方法需要 `return`。如果 `title = title` 没有效果，比较参数与字段的含义。先实现普通输入，再一次加一条边界。阅读只需 [Dev.java 的面向对象与异常入口](https://dev.java/learn/)，不必看完全部 Java 教程。

| --- | --- | --- |

| B 状态与派单 | 3 小时 | 定义四种 `TicketStatus`；新增工单为 `OPEN`；加可为空的 `Long assigneeId`，仅实现 `assign(long engineerId)`：正数编号、只允许 OPEN，成功转 IN_PROGRESS |
| C 筛选与去重 | 3 小时 | 用普通循环筛选状态并生成新列表；用 `Set<Long>` 检查重复编号；写一个统计数组数字出现次数的小练习 |
| D 写文件 | 3 小时 | 用 `Properties` 把字段变成字符串，再用 UTF-8 Writer 保存；明确文件的绝对位置；保存前先保留上一份练习文件 |
| E 读文件 | 3 小时 | 读回字符串、解析编号与枚举、恢复对象；缺文件视为首次启动，坏数据报清字段且停止加载，不能默默当空数据覆盖旧文件 |
| F 重启验收 | 3 小时 | 保存后结束进程，再启动；新增编号使用现有最大编号加 1；验证重复编号、坏状态、中文与特殊字符，独立说明转换过程 |

`List` 适合按顺序遍历；`Map` 用编号直接定位工单；`Set` 记录“某编号是否出现过”。集合里存的是对象引用，并不会自动把数据写入硬盘。枚举将可选状态限制为 `OPEN`、`IN_PROGRESS`、`RESOLVED`、`CLOSED`；本周只实现前两种之间的派单，处理与验收留到第 9 周。

文件使用现成的 `Properties` 格式，避免自己设计逗号和换行的转义。约定键为 `count`、`ticket.0.id`、`ticket.0.title`、`ticket.0.status`、`ticket.0.assigneeId`，后续记录按下标递增。编号等数字用十进制字符串；未派单的处理人保存为空字符串。这个下标只是文件位置，不是工单编号。库会处理标题里的 `=`、反斜杠和换行；不要自己按 `=` 切割文件。[Java Properties 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Properties.html)

读取旧数据需要单独的 `restore` 工厂方法或仅供存储层使用的构造器；仍校验编号、标题、状态，以及 OPEN 没有处理人、其他状态有正数处理人。不要为了恢复文件开放任意 `setStatus`。`try-with-resources` 在正常或异常退出时关闭 Reader/Writer；“关闭”与“捕获异常后假装成功”是两件事。

验收：1、2、3 三张中把 2 派给工程师 20，筛选 OPEN 得到 1、3；重启后仍是同样结果，新工单编号为 4。把文件中的一个状态改成 `DONE`，启动应指出对应记录不合法并保留原文件；修回去后可加载。标题 `A=B\\C` 保存读取后完全一致。重复派单抛异常，处理人不改变。

自测：①`Map.put` 遇到已有编号会怎样，创建工单该怎么处理？②为什么重新启动后不能让编号从 1 开始？③程序打印“保存成功”但重启找不到文件，先查哪两件事？

卡住提示：先只保存、读取一张工单的标题，再加编号、状态和循环。先让内存程序跑通再接文件；本周不实现文件并发写入或自定义二进制序列化。

接口是调用方与实现方的约定。例如业务只需要“按编号找工单”，无需知道它来自 Map 还是文件。构造器传入依赖，就是创建 Service 时把它需要的 Repository 交给它。这会让接数据库时保留业务规则，必要时调整新增/查询的存储契约，不是为了多建几个空类。

接口可以采用下面的签名，`Optional.empty()` 表示不存在。`add` 遇到同编号应报错；`update` 找不到原编号也应报错。返回新 List 防止调用方直接增删仓库的集合；其中的 Ticket 仍可能是同一对象，修改后必须显式调用 `update`，不要依赖内存引用恰好同步的效果。

```java
public interface TicketRepository {
    void add(Ticket ticket);
    Optional<Ticket> findById(long id);
    List<Ticket> findAll();
    void update(Ticket ticket);
}
```

验收：把 `new InMemoryTicketRepository()` 换成 `new FileTicketRepository(path)`，创建、查询、改标题和派单结果一致；文件版每次成功修改后保存，重启数据保留。保存失败必须报告失败，不能打印成功。输入不存在的编号 999 显示“工单不存在”；关键词“投影”只返回包含该文字的工单；用 Maven 构建出现 `BUILD SUCCESS`，打包后从命令行运行同一入口。

Maven 负责按配置取依赖、编译、测试与打包；它不会自动替你写业务。首次联网准备好 Maven、插件和依赖，之后无新增依赖时可尝试离线构建。`maven.compiler.release` 指定目标 Java 版本；不要只改 IDEA 的字体旁语言级别就认为终端同步了。参考 [Maven 入门与目录结构](https://maven.apache.org/guides/getting-started/maven-in-five-minutes.html)及[编译目标版本](https://maven.apache.org/plugins/maven-compiler-plugin/examples/set-compiler-release.html)。

自测：①为什么业务类不应在自己的方法里反复 `new FileTicketRepository(...)`？②将存储实现换掉后，哪些类应变化，哪些规则应保留？③IDEA 能跑但 Maven 报 `release version 21 not supported`，你要检查什么？

卡住提示：先保留 `TicketDemo` 直接调用 Service，不必做复杂菜单。环境不通时先写接口和内存实现；正式进入 Web 前必须解决构建问题。

表是一类数据，行是一条记录，列是字段。主键 `id` 用于稳定识别记录；名字可以变化，所以不能靠“投影仪”唯一识别设备。外键要求工单引用的用户和设备存在，但它不自动判断用户是不是工程师，也不判断设备是否启用，这些要在业务层检查。数据库约束是额外保障，不替代 Java 的清晰错误提示。

字段固定为 `app_user(id, username, password_hash, role, enabled)`，`device(id, code, name, location, enabled)`，`ticket(id, title, description, device_id, reporter_id, assignee_id, status, version, created_at, updated_at)`。`assignee_id` 初始为 SQL NULL，版本号初始 0；创建时间、更新时间用 DATETIME(6)，本地学习统一按 Asia/Shanghai 解释，部署时再统一应用与数据库时间设置。完整类型和关键 DDL 在参考答案中。

| 样本 | 明确内容 |
| --- | --- |
| 用户 | 1 reporter_a 为 REPORTER；2 engineer_a 为 ENGINEER；3 admin_a 为 ADMIN；4 reporter_b 为 REPORTER，均启用 |
| 设备 | 1 PJ-001 投影仪；2 AC-001 空调；3 PR-001 打印机，均启用 |
| 工单 101 | 投影仪无法开机，设备 1，报修人 1，OPEN，无处理人 |
| 工单 102 | 空调不制冷，设备 2，报修人 1，IN_PROGRESS，处理人 2 |
| 工单 103 | 投影画面闪烁，设备 1，报修人 4，OPEN，无处理人 |

密码列只放 `NOT_A_LOGIN_HASH` 这一显式占位值；本阶段没有登录功能。第 12 周必须通过 PasswordEncoder 生成真正的密码哈希，不能把占位值或明文当作可登录数据。

验收：查 OPEN 返回 101、103；查报修人 1 返回 101、102；查未派单用 `IS NULL` 返回 101、103。插入重复 `PJ-001` 失败；引用设备 999 的工单失败；把设备 1 停用后，其历史工单仍可查询。保存自己写的 SQL，不依赖图形工具自动生成全部语句。

自测：①`assignee_id = NULL` 为什么不是正确查询？②设备名称修改后，为什么不应逐条修改工单里的设备编号？③外键存在，能否保证派给用户 1 的工单合理？

卡住提示：先只建 device 表练 INSERT/SELECT，再建其余表。连不上时区分服务未启动、端口错和账号错；不要重装所有软件。参阅 [MySQL 建表](https://dev.mysql.com/doc/refman/8.4/en/creating-tables.html)，已有 8.0 环境可先练本阶段通用 SQL。

| F 复写与验收 | 3 小时 | 独立写 LEFT JOIN 统计；补一个字符串或哈希表算法小题；写事务失败时该怎么做，回答自测 |

JOIN 根据编号把行拼成结果；LEFT JOIN 会保留左侧没有匹配项的行。因此未派单的工单也应出现在列表中。GROUP BY 将同一组放在一起计算。对“所有设备及其工单数”，没有工单的设备仍占结果的一行，应该统计右表非空工单编号，而不是简单数结果行。[MySQL JOIN 语法](https://dev.mysql.com/doc/refman/8.4/en/join.html)

事务把几个修改当作一个工作单元。只有提交后才确认这些修改；主动回滚会撤销尚未提交的修改。本周用设备位置更新做小实验，下阶段才把工单状态与操作日志一起提交。SQL 报错后不要假设整个事务自动回滚；练习时明确执行 ROLLBACK。建表、改表等 DDL 不拿来演示普通事务回滚。[MySQL 提交与回滚](https://dev.mysql.com/doc/refman/8.4/en/commit.html)

索引像按某种顺序整理的查找入口，会占空间并增加写入维护成本。联合索引 `(reporter_id, created_at, id)` 对本周查询有合理的使用场景，但优化器仍按成本选计划。三条样本走全表扫描并不等于索引错误。重点是解释 `possible_keys`、`key`、`rows`、`Extra`，不要编造百分比。

验收：关联列表仍有 3 行，101 和 103 的处理人显示为空或“未派单”；状态统计为 OPEN 2、IN_PROGRESS 1；设备统计为投影仪 2、空调 1、打印机 0。样本时间依次为 09:00、10:00、11:00，第一页编号 103、102，第二页 101。设备 1 位置改为“临时位置”后回滚，恢复原值；改为“新教室”并提交，再连接仍是新值。

自测：①处理人使用 INNER JOIN 为什么可能丢工单？②统计打印机工单数为什么不能直接用 COUNT(*)？③事务中第一条更新成功、第二条失败，为什么仍要显式回滚？

卡住提示：先只关联 ticket 与 device；结果正确再加两个用户别名。事务每次只做一个实验，记录原值，结束时确保 COMMIT 或 ROLLBACK，避免连接一直持有未提交修改。

JDBC 是 Java 操作关系数据库的一套接口，MySQL 驱动负责具体连接和通信。Connection 是这次数据库会话；PreparedStatement 保存 SQL 结构和绑定参数；ResultSet 保存查询结果，游标先位于第一行之前，要先 `next()` 才读取。`?` 只绑定数据值，不用来绑定表名、列名或排序方向。

本单元先写 `JdbcTicketQueryDemo` 做按id只读查询，再在练习库做回滚更新；随后创建课单独学习插入与生成主键。创建方法接受标题、描述、设备编号、报修人编号，返回数据库生成的 long id；进入数据库后编号由数据库生成。不要为了兼容原来带 id 的构造器，让新增工单乱填一个假编号；可以先完成插入，得到 id 后再构造对象。业务时间与状态使用前述约定，SQL 列表写全，不依赖列的物理顺序。

HTTP 把请求与响应带过网络，JSON 是其中一种数据格式。`GET /api/tickets/101` 读取工单；`POST /api/tickets` 提交新工单。下一阶段正常创建返回 201，查询成功 200，参数错误 400，不存在 404。最终报修人来自登录身份，本周控制台传编号只是没有登录时的学习接口。[HTTP 概览](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)

验收：新增 `"  O'Reilly投影仪异常  "`，数据库保存去掉两端空格的原文字，单引号不破坏 SQL；退出程序后按新 id 查得到。创建时设备为 999，外键拒绝且记录数不增加。查询 999999 无结果；SQL NULL 映射成 `Long null`，不是编号 0。查 OPEN 在初始样本上返回 101、103，新增 OPEN 工单后也能返回它。

自测：①为什么不把标题直接拼进 SQL 字符串？②为什么 Java 程序结束后数据还在，而第 2 周的纯 Map 不在？③收到 200 和 JSON 是否代表一定查到了想要的工单，还应核对什么？

卡住提示：连接不通时先用同一主机、端口和账号在数据库客户端连接；能连接后再查驱动与依赖。`No suitable driver` 与 `Access denied` 原因不同。这里的 JDBC 是理解数据访问的桥梁，不继续扩成另一套正式持久层。参考[驱动接入](https://dev.mysql.com/doc/connector-j/en/connector-j-installing-maven.html)与[DriverManager 连接说明](https://dev.mysql.com/doc/connector-j/en/connector-j-usagenotes-connect-drivermanager.html)。

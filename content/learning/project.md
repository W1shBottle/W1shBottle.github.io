现有Controller→Service→Repository可以复用为Agent的业务基础。先完成数据库业务与必要权限，再在Service外封装工具；当前查询方法还没有鉴权，不能直接作为已授权工具公开。

## 同一个项目的阶段交付

路线：**A 后端业务与基础工程 → B 模型调用入门 → G 只读运维 Agent → C 知识检索与评测改进**。G为明确主线，C保留原评测编号并补知识检索；评测贯穿B/G。

| 阶段 | 项目交付 | 进入下一步的证据 |
| --- | --- | --- |
| A1 最小后端业务 | Boot/MyBatis/MySQL，创建→派单→解决→验收，详情与必要筛选 | 请求真实落库、数据库生成主键；本人能解释调用链并独立改一个筛选或规则 |
| A2 基础工程 | 身份/角色/归属、参数与异常、状态日志同事务、版本冲突/重复请求、关键测试、可复现启动 | 拒绝越权/非法迁移；故障回滚、竞争请求、重启和一次排错有证据 |
| B 模型调用入门 | 对有权访问的工单生成摘要、分类建议、待补充信息，只展示参考 | 真实API记录、输出校验、超时/无效输出回退可核对；同时开始评测，达标即进入G |
| G 只读运维Agent | 查可见工单、读详情，追问→工具调用→结果整合；上下文、任务状态和执行步骤持久化 | 单工具到有限多步实际可跑；中断可解释、补信息可继续、工具失败/越权/超限有明确退出 |
| C 知识检索与评测改进 | 小型运维资料检索、可定位引用、固定任务集、基线、失败归因和回归 | 区分检索/工具/生成错误；报告真实任务完成率、延迟和用量成本，展示一次改进与剩余失败 |


最终场景：查询本人报修工单，读取状态和处理记录，必要时追问设备，再检索维护资料并给有出处的跟进建议。所有数据来自虚构教学场景，不连接真实硬件。

## 第一版业务边界

设备来自虚构园区/实验室记录，无真实硬件连接。只保留三种角色：

| 角色 | 首版职责 | 不可越过的边界 |
| --- | --- | --- |
| REPORTER 报修人 | 选启用设备、创建、查自己的工单、验收 | 不能冒充别人报修、查询别人记录或自行派单 |
| ENGINEER 工程师 | 查分给自己的工单、提交非空处理说明 | 不能处理别人名下工单或代报修人验收 |
| ADMIN 管理员 | 查询、给 OPEN 工单指定启用工程师 | 不能随意设置状态或代报修人验收 |

流程为 OPEN→IN_PROGRESS→RESOLVED→CLOSED。首版不做验收退回、评论、公开注册、全套设备/用户后台、统计大屏。演示先用接口工具，随后可加简洁页面；不要求先学大型前端框架。

现有三表保留，A 阶段再加 ticket_action_log；处理说明存 resolve 动作 note，状态与日志同事务。暂不建 ticket_comment/ticket_resolution。创建重试用请求键，状态操作用前置状态＋期望版本；SQL 中 version 字段存在并不代表这些保护已实现。

具体规则、接口与验收不在本页重复维护，以项目 [需求](/learning/project-requirements/)、[设计](/learning/project-design/)、[验收](/learning/project-verification/) 为准。

## 第一项 AI 功能为什么这样选

工单经常只有杂乱描述。A阶段完成 title/description 等字段映射后，就能支持“整理现象、给分类建议、指出缺的信息”，无需先做知识库或购置硬件。第一版对有权读取的工单返回 summary、category、missingInformation；category 限定 DISPLAY/PRINTING/HVAC/OTHER/UNKNOWN，只作为建议，不自动入库派单。首版只展示/复制参考，不直接写回标题。当前 rename 只有控制台和 Service 实现；以后要做人工采纳入口，先补明确权限、状态、版本和日志规则的 HTTP 接口。

这项功能能够练习真正的模型请求、响应结构、输入边界、成本和失败处理。AI 无依据时不编造型号/维修结论；模型不可用时正常报修、派单和验收继续运行。第一版不能声称故障诊断专家或自主维修 Agent。

B 开始前再选择供应商、模型与费用上限，准备本地环境变量；当前未配置或真实验证任何模型。Java 先实现清晰的 ModelClient 边界，调用 API，不强行拆 Python 服务。模拟响应只能验证解析与降级，不能充当真实模型效果。

## G只读Agent与C知识检索（明确目标）

- G在B达标后实施：findVisibleTickets/getTicketDetail工具、参数与返回契约、模型请求工具→Java执行→结果回传、有限多步与追问。
- Java从会话取身份并逐次鉴权，限制结果量/步数/耗时/调用数；上下文隔离，失败有明确退出。
- 持久化taskId、任务状态和步骤；能查看历史、等待补信息后继续，重启中断有可解释行为。先覆盖单进程恢复，不做分布式调度。
- C准备少量有来源说明/版本/适用设备的虚构维护资料，接searchMaintenanceDocs，回答附资料ID/段落；查不到依据就说明不足。先关键词检索，再按实验补向量召回。
- B/G开始保存固定案例，C集中比较检索、工具、任务完成、延迟与成本；模拟故障与真实模型效果分开。
- 写工具、MCP、SubAgent及模型路由后置；不把Redis/MQ/微服务/K8s、Python服务、模型训练作为B/G先修课。

## 技术与学习方式

沿用 Java 21、Maven；当前MySQL8.4.13与Connector/J26.10.0已经过独立恢复和连接验证。SQL与短JDBC查询/更新回滚已有跟练，Spring Boot已接文件版业务；下一步收尾错误响应并接MyBatis/MySQL业务，不重复升级现有环境。框架版本到接入时按官方兼容表固定；认证仍优先Spring Security＋Session Cookie，保留CSRF并使用框架密码编码器。

两种 AI 学习分开：AI 辅助编程可用于解释/评审/排错，但每个模块要自己读调用链、独立改需求并验证；产品内 AI 功能则必须自己接入、测试真实 API 和失败路径。安排少量高价值测试，避免重复抄同类断言；数据库事务必须用真实 MySQL 验证，不能只看 Mock。

每次约 3 小时是时间预算，不是作业定额：先回忆已有代码，再讲一个新概念、独立写一个小变更、验证并记录帮助和困难。每个阶段至少独立实现/修改一个功能、解释一次设计、排查一个故障。完整任务见 [阶段学习计划](/learning/schedule/)。

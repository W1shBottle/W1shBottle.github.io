## B：已有工单摘要与分类建议

目标：已创建工单有口语化故障描述，服务端在确认当前用户可见后读取真实描述，AI整理摘要、类别建议和需补充的信息，帮助阅读和跟进。**不生成设备维修操作指令，不自动派单、解决或验收。** Java继续负责确定性业务规则，用户审阅；后续人工操作仍走普通业务接口。

### B1 先理解模型API，再写最小客户端

你需要亲手完成：从配置取端点、模型名和环境变量key；绑定有限连接/请求超时；发送一条虚构描述并读取结果。记录提供方、模型、调用时间和脱敏响应。日志不打印key、Cookie、密码或完整敏感描述。

待配置清单：可访问的API端点、模型标识、凭据、额度/预算、计费币种及价格依据、输入输出长度限制。现在没有选定提供方或key，不把文档中的示例当真实调用。没有配置时可以完成本地客户端契约测试，状态写“真实模型验证待完成”。

### B2 将输出限制成业务可用数据

未来 `ai/AiAssistanceService.java` 通过 `ModelClient` 获取建议；未来API `POST /api/tickets/{id}/ai-assistance` 复用当前登录和错误处理。输出只有三个字段：

```json
{
  "summary": "空调制冷异常并伴随滴水",
  "category": "HVAC",
  "missingInformation": ["异常开始时间", "所在房间"]

```

这只是**输出契约示例，未发生模型验证**。分类可先约定DISPLAY、PRINTING、HVAC、OTHER、UNKNOWN；Java做枚举/字段/长度校验，不因模型返回JSON就信任其内容。输入不足时使用UNKNOWN并建议补充；不能据此猜故障根因或生成维修指令。类别是建议展示，不必立刻修改ticket表。

你需要亲手完成：按路径id通过原详情授权读取description，限制上下文长度、对空描述给可理解提示；反序列化三个字段；缺字段/非法枚举/超长摘要进入失败分支；页面或HTTP结果明确标注“建议，请核对”。服务端先按路径id检查资源可见性，再读取真实description，不把客户端传来的描述或reporterId当作已授权事实。第一版只展示建议，不增加自动写入或新建前建议流程。

**进入B3的标准：** 自己修改一个类别或长度约束，并同步DTO、解析和一条有意义的测试；能解释“结构合法”和“语义正确”是两回事。官方结构化输出说明也提醒不能把转换视为绝对保证，仍需应用验证：[Spring AI结构化输出](https://docs.spring.io/spring-ai/reference/api/structured-output/converters.html)。阅读该概念不要求安装Spring AI。

### B3 超时、错误、日志与人工回退

对超时、429、5xx、坏JSON、缺字段分别准备可控制的客户端替身，用来测试本地分支。限制总耗时与重试次数；只对明确可恢复故障考虑有限重试，认证失败和结构错误不循环重发。模型调用位于数据库事务外，不持有工单锁等待网络。

你需要亲手完成：失败时返回可理解的“建议暂不可用”，保留用户原输入；关闭AI配置后，人工创建、查询、派单、解决、验收照常。记录requestId、模型、promptVersion、耗时、结果类别、已知token用量；来源未提供用量时写unknown而非0，不能推算为免费。

**B验收：** 真模型能产生至少一组可核对建议；故障测试证明人工业务不被AI阻断；真实调用与模拟故障两类记录分别标清。该阶段无需RAG、向量库、多步任务或Agent。

### C1 运行前先定验收方法

先准备约20个虚构案例，并按下列类型分组。期望应是规则和可接受范围，不强求模型每次逐字相同。开发调试与最终留出案例分开，调整提示词后也跑留出案例，不能只展示调试成功的输入。

| 类型 | 检查什么 |
| --- | --- |
| 正常明确 | 摘要保留设备/症状关键事实；类别可接受 |
| 模糊或信息少 | 不补造房间/时间/原因；missingInformation提出有用补充 |
| 不支持类别/无依据 | OTHER或UNKNOWN；不假装诊断成功 |
| 中文、引号、长输入 | 长度受控、编码正确，拒绝超限；文本不破坏结构 |
| 文本要求越权或改规则 | 仍只输出建议；不会替换会话身份或调用写操作 |
| 超时、429、5xx、坏结构 | 有界失败，人工报修仍可完成，日志可定位 |

测试模拟器负责故障分支，真实模型负责质量判断；不将模拟器固定返回值计入模型质量分数。无密钥时本节质量/成本保持待验证。

### C2 对照与度量

先对同一批已有工单描述进行人工阅读和摘要整理，记录完成时间和必要修改次数；再查看建议并人工修正摘要，比较建议可用比例、关键事实遗漏/新增、修改次数与耗时。小样本只反映这批任务，不宣称普遍提升或真实用户收益。

每次记录：caseId、模型/提示词版本、运行日期、成功或失败原因、最终建议、人工判定、端到端延迟、输入/输出tokens、重试次数、实际账单或明确的估算公式。费用以当次提供方价格为据，标清币种/日期；无用量则未知。响应时间可报告中位数和较慢样本，样本足够再报告P95。

先写下验收阈值再跑：权限绕过或AI故障阻断主业务必须0；输出结构违规必须被Java拦截；质量与建议可用率采用明示的目标和真实分母，没达到就说明不足，不能换掉失败案例凑分数。人工评价保留判定理由。

### C3 用失败案例推进，不盲加组件

从最常见失败选一类：摘要遗漏、分类含糊、输入过长或过度猜测。只改一个因素，如提示词、schema、上下文裁剪或模型配置，再重跑固定案例与留出案例。记录提升和退化；旧失败样本转成回归项。

**C验收：** 能讲清相比不用AI具体改善了什么，展示一条仍失败的例子和限制，复现一次改进前后比较；依然可以关闭AI跑完整业务。形成可演示小版本后再按实际岗位缺口决定下一项，不另开第二个大项目。

## 按需升级：RAG和受控Agent

**RAG任务触发条件：** 用户需要回答项目维护资料中的问题，且已有可使用资料。先准备少量虚构故障资料和来源清单；导入记录sourceId/版本/权限，切分与检索结果可追踪，回答引用能定位原段落。先验收检索命中、无命中、无权限和过期资料，再接生成；无证据时明确不足，不写虚构来源。不预设必须购买向量数据库。

**只读Agent触发条件：** 自然语言查询确实需要组合多个已有业务查询。先只开放 `findVisibleTickets`、`getTicketDetail` 等白名单工具，复用原Service的身份和资源范围；模型不能传任意SQL、URL或授权身份。限制工具步数、总耗时、返回条数、上下文和预算；工具异常立即给可理解的终止或降级结果。上下文只保留该会话必要数据，下一用户不能继承上一用户的工单内容。

用固定案例检查：正确查到本人数据、模糊条件要求澄清、无结果、不存在/无权限编号、工具失败、模型重复调用、超过步数。先证明一次只读工具调用可靠，再尝试多步骤；工具实际执行和校验由应用承担：[Spring AI工具调用说明](https://docs.spring.io/spring-ai/reference/api/tools.html)。不因叫Agent就必须引入框架或多个模型。

未来若增加写工具，先显示待执行动作/参数并在需要时取得用户确认，确认后仍由Java重新鉴权、校验参数/状态/version、处理重复请求。不能把模型意图或用户文本里的“管理员”当作权限，也不能让确认绕过数据库约束。只读工具和评估尚未可靠时，自动派单/关闭继续延后。

| 两个独立连接或两个独立请求并发派单，重复验证并检查数据库 | 4 | 成功一次、冲突一次、有效日志一条 |
| 复盘事务边界，做两道哈希表或二分题，完成自测 | 3 | 三题答案和一条有意义的提交 |

两个请求都曾经读到 OPEN，并不代表它们更新时仍然有权派单。事务保证几条操作共同成功或失败；“本次修改必须基于我读到的旧状态”还需要写入条件。Java 的 `synchronized` 可以保护同一个 JVM 内共享的锁对象，却不能独自协调两台应用之间的数据库修改。

下面是 MyBatis XML 中的局部 SQL。Java 参数 `expectedVersion` 对应数据库字段 `version`；`assigneeId` 先验证确实是启用的 ENGINEER，操作者身份来自登录会话。

```sql
UPDATE ticket
SET assignee_id = #{assigneeId},
    status = 'IN_PROGRESS',
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = #{id}
  AND status = 'OPEN'
  AND version = #{expectedVersion};
```

更新返回 1 才写入 ASSIGN 操作记录；返回 0 表示这次操作没有获准，不能假装派单成功。本项目先检查是否存在和是否有权限，再把条件更新失败映射为 HTTP 409；页面提示刷新。`ticket_action_log` 的 `actor_id` 来自会话，`from_status` 为 OPEN，`to_status` 为 IN_PROGRESS。Service 对外事务方法要经过 Spring Bean 调用，不能只在同一个类的内部自调用处贴注解。[Spring 事务说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

实验采用测试库中的新工单，记录初始版本。两个工作线程都先拿到同一版本，再用 `CountDownLatch` 同时放行；各自调用 Service 或分别发出 HTTP 请求。不要用一个 JDBC Connection 给两个线程共享。仅连续点击两次页面，只验证了重复请求，不能证明发生过并发。

**验收：** 同一初始版本下恰好一次成功；最终状态 IN_PROGRESS，版本只增加 1，处理人是胜出请求选择的人，有一条有效派单日志。没有第二位工程师账号时可以都派给 engineer_a，仍然检查两次结果；需要验证覆盖时，再创建独立测试工程师。连续执行至少五轮，每轮创建新工单，保存结果。一次请求失败并不意味着数据库故障。

**卡住时：** 两次都成功，先看 WHERE 是否带旧版本和状态；两次都失败，先检查初始状态、版本、角色与 CSRF；日志有两条，检查是否在判定更新结果之前插日志。不要先加入 Redis 锁。

**自测：** 14.1 为什么 `SELECT` 后判断 OPEN，再无条件 `UPDATE` 会出错？14.2 为什么有事务还需要条件更新？14.3 派单已经更新，写操作记录时抛出异常，最终数据库应是什么样？

先优化真实存在的列表查询，如报修人查看自己的某种状态工单。下面只是候选设计，是否有效由数据分布和实际执行计划决定，不要求 MySQL 必须选择它。

```sql
EXPLAIN
SELECT id, title, status, created_at
FROM ticket
WHERE reporter_id = 1 AND status = 'OPEN'
ORDER BY created_at DESC, id DESC
LIMIT 20;

CREATE INDEX idx_ticket_reporter_status_time
ON ticket (reporter_id, status, created_at DESC, id DESC);
```

索引能缩小定位范围或帮助排序，但会增加空间与写入维护成本。不能给每个字段都加一个索引就称作优化。阅读 `key`、`rows`、`Extra`；传统 EXPLAIN 的行数是估计，支持的 SELECT 可以用 `EXPLAIN ANALYZE` 看真实执行情况，它会实际执行查询。[MySQL EXPLAIN 文档](https://dev.mysql.com/doc/refman/8.4/en/using-explain.html)

固定数据量、过滤条件、机器和应用版本，先预热，再重复测量，例如各测 10 次，保留中位数和执行计划。只有几十行或耗时接近计时噪声时，如实写“差异不足以判断”，不要生成一个漂亮百分比。不要把 SQL 客户端耗时直接当成整个接口响应时间。

线程池实验使用 `corePoolSize=2`、`maximumPoolSize=2`、容量为 2 的 `ArrayBlockingQueue` 和 `AbortPolicy`。让前两项任务在门闩等待，再提交另外三项，观察第五项被拒绝；最后释放门闩、等待结果并关闭池。池限制正在执行的任务，队列限制等待任务；任务异常也要通过结果或日志观察。[Java 21 ThreadPoolExecutor](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)

JVM 本周只要求分清：对象通常占用堆；线程执行方法需要自己的栈帧；GC 回收不可达对象，并不保证数据库连接等外部资源被及时关闭。可以用 `jcmd -l` 找到自己的 Java 进程，再按 JDK 帮助检查堆信息。不要为了练习故意把个人电脑内存耗尽。

**验收：** 一条 SQL 优化有前后证据与局限；能解释线程池拒绝为何发生；实验退出后没有挂住的工作线程；能说出增加索引、线程数、堆大小各自不能解决的至少一个问题。

项目讲解按一个具体请求展开：谁报修，Controller 接收什么，Service 怎样校验角色与业务规则，Mapper 执行哪条 SQL，事务怎样覆盖工单和日志，失败怎样返回。再选择一个难点，比如并发派单，讲出原来的错误、两个请求的交错、修复条件、验证结果和仍有的限制。

5—8 分钟演示可以这样分配：1 分钟业务与角色；2—3 分钟工单流程；1 分钟权限边界；1 分钟并发或回滚证据；1 分钟部署、真实问题与下一步。不要花一半时间读依赖名称。单人学习项目就说个人项目；请同学帮忙测试可以如实说测试协助，不能改写成企业团队交付。

第一次模拟面试用 45 分钟：自我介绍 3 分钟，Java 与集合 10 分钟，SQL 与事务 10 分钟，项目追问 12 分钟，编码或 SQL 10 分钟。独自练习时随机抽问题，用手机录音，回答结束后再看笔记。第二轮换问题顺序，检验是否依赖背诵。

限时小改任选一项：列表增加设备筛选且保留资源权限；限制评论长度并增加边界测试；管理员统计增加一个状态条件。先说影响范围，再修改 DTO、Service/Mapper、测试和文档，40—60 分钟内完成可用的小部分，不要求一次做完全部可能扩展。

**验收：** 不看稿能讲清三项设计取舍；能展示一条真实排错记录；权限、事务和并发至少各回答一次追问；README 在新目录或另一环境可复现到已完成的程度；简历的每项功能确实存在。未掌握的问题写进待补清单，不填成“精通”。

**卡住时：** 忘词就画“请求 → Service → SQL → 返回”；遇到不会的问题先说明已知边界，再给出准备怎样验证；面试反馈涉及基础就补一个实验，不整套重学。未完成扩展时，把时间优先留给申请和反馈修补。

**自测：** 20.1 用一分钟说明你怎样防止两次派单互相覆盖。20.2 面试官问“你项目支持多少并发”，没有正式压测时怎样答？20.3 列表新增设备筛选时，要改哪些地方，怎样证明权限没有退化？

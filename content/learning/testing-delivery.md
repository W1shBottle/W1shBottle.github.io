## R：Redis课程与工单实践（待学）

## B：Python模型调用入门

先在Python脚本中使用虚构工单，输出summary/category/missingInformation。可先做不连网的模拟客户端检查字段和异常，再用一个可用模型API完成真实调用；模拟结果不当成模型效果。模型名、key、预算从环境配置；设置超时、限制重试，记录错误类别与用量，未知成本写未知。

模型的JSON仍需程序校验类型、必填和枚举；没有依据时应明确缺失信息。不要把真实用户信息、凭据或未经允许的资料发送给模型服务。使用模型生成摘要只是AI功能，还不是已完成Agent。

## G：Python只读Agent

先让模型在虚构数据上选择 `list_tickets` / `find_ticket` 一类受控工具，Python校验参数并执行，再返回工具结果；记录模型请求、工具名、结果摘要、最终回答。先单次，再加入多步骤、歧义追问、最大步数、超时和上下文隔离；日志不保存密钥或不必要原文。

有明确状态流需求再学习LangGraph；可先用模型SDK或LangChain实现单工具，不要求把所有框架一起学。后续保存任务状态和每步记录，等待补充后继续，重启可恢复或明确中断；不提前搭分布式调度。

## L：与Java工单服务联调

先让Python用HTTP访问本机、隔离演示数据的只读Java接口，约定参数、JSON、404、超时及失败。Java现有开发接口尚未认证授权，不能声称它已支持多用户安全访问，也不连接真实敏感数据。连接真实工单前，先实现用户身份、资源归属和服务间身份传递，Java每次检查授权；模型给出的userId不是身份。模型不能执行任意SQL/命令，也不能直接派单或关闭。

将来如果要从Java页面启动Python助手，再增加明确的服务调用、超时和错误处理。两个服务意味着独立环境、启动、日志和部署成本，不强制提前引入微服务、中间件或容器编排。

## C：资料检索与评测

从约12—20条测试起步并逐步增加，覆盖正常查询、歧义追问、无结果、坏参数、工具失败、超限、越权和重复调用。分开记录工具选择/参数、检索依据、结果质量、耗时、调用量与成本；真实模型与模拟故障分开。改动一次因素后回归，并保留失败案例。

**目标：同一张 OPEN 工单被两次同时派单时，只允许一个请求成功，失败者得到明确冲突。** 先确认上周的角色与数据权限已经通过检查。

| 本周任务 | 小时 | 做完留下什么 |
| --- | ---: | --- |
| 用两个线程运行简单计数实验，认识共享变量、原子性、`start` 与 `join` | 3 | 一段小实验和自己的运行解释 |
| 画出两个管理员先查询再更新的交错过程，复现旧写法的覆盖问题 | 3 | 六步时序记录，保留失败证据 |
| 写条件更新 SQL，检查受影响行数，把状态更新和操作记录放进一个事务 | 5 | 派单 Mapper、Service、冲突响应 |
| 两个独立连接或两个独立请求并发派单，重复验证并检查数据库 | 4 | 成功一次、冲突一次、有效日志一条 |
| 复盘事务边界，做两道哈希表或二分题，完成自测 | 3 | 三题答案和一条有意义的提交 |

两个请求都曾经读到 OPEN，并不代表它们更新时仍然有权派单。事务保证几条操作共同成功或失败；“本次修改必须基于我读到的旧状态”还需要写入条件。Java 的 `synchronized` 可以保护同一个 JVM 内共享的锁对象，却不能独自协调两台应用之间的数据库修改。

下面是 MyBatis XML 中的局部 SQL。Java 参数 `expectedVersion` 对应数据库字段 `version`；`assigneeId` 先验证确实是启用的 ENGINEER，操作者身份来自登录会话。

```sql
UPDATE ticket
SET assignee_id = #{assigneeId},
    status = 'IN_PROGRESS',
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = #{id}
  AND status = 'OPEN'
  AND version = #{expectedVersion};
```

更新返回 1 才写入 ASSIGN 操作记录；返回 0 表示这次操作没有获准，不能假装派单成功。本项目先检查是否存在和是否有权限，再把条件更新失败映射为 HTTP 409；页面提示刷新。`ticket_action_log` 的 `actor_id` 来自会话，`from_status` 为 OPEN，`to_status` 为 IN_PROGRESS。Service 对外事务方法要经过 Spring Bean 调用，不能只在同一个类的内部自调用处贴注解。[Spring 事务说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

实验采用测试库中的新工单，记录初始版本。两个工作线程都先拿到同一版本，再用 `CountDownLatch` 同时放行；各自调用 Service 或分别发出 HTTP 请求。不要用一个 JDBC Connection 给两个线程共享。仅连续点击两次页面，只验证了重复请求，不能证明发生过并发。

**验收：** 同一初始版本下恰好一次成功；最终状态 IN_PROGRESS，版本只增加 1，处理人是胜出请求选择的人，有一条有效派单日志。没有第二位工程师账号时可以都派给 engineer_a，仍然检查两次结果；需要验证覆盖时，再创建独立测试工程师。连续执行至少五轮，每轮创建新工单，保存结果。一次请求失败并不意味着数据库故障。

**卡住时：** 两次都成功，先看 WHERE 是否带旧版本和状态；两次都失败，先检查初始状态、版本、角色与 CSRF；日志有两条，检查是否在判定更新结果之前插日志。不要先加入 Redis 锁。

单元测试检查某条规则，接口测试检查输入、会话、返回码，数据库集成测试检查真实 SQL 和事务。模拟 Mapper 抛异常可以验证 Service 如何响应，但模拟数据库不能证明 MySQL 回滚正确。测试名称写行为，例如 `reporterCannotReadOthersTicket`，不要只叫 `test1`。测试依赖使用所选 Boot 版本管理的 `spring-boot-starter-test`，Web MVC 和 Security 的测试支持按同版本文档添加，不单独拼装一组旧 JUnit 版本。[Boot 测试文档](https://docs.spring.io/spring-boot/reference/testing/index.html)

最少覆盖这八项：有效创建、空标题、报修人越权查询、错误工程师处理、非法状态迁移、重复验收、并发派单、操作记录写入失败后的回滚。登录验证再保留正确密码、错误密码、退出后三条。对 Session 应用，修改请求的测试需要有效 CSRF；缺少 CSRF 的 403 不能证明角色授权做对了。[Spring Security 测试 CSRF](https://docs.spring.io/spring-security/reference/servlet/test/mockmvc/csrf.html)

先做数据库隔离护栏：测试连接只指向 `ops_ticket_test`，测试账号无权写开发库；开始测试时查询 `SELECT DATABASE()` 并断言库名。每个测试创建自己的数据，记录主键，按依赖顺序清理自己创建的记录。不得用“清空所有表”解决残留问题。使用固定样本时，明确它属于测试库，不与正在演示的实例共用。

验证回滚时，真实调用 Spring 管理的 Service：让工单更新实际执行，再让日志写入因测试故障失败，最后重新查询工单与日志。测试本身若带自动回滚事务，可能掩盖业务事务缺失；这项测试不要依赖外层测试事务。真实端口的 HTTP 请求在服务端线程里执行，也不会自动跟随测试线程回滚。[Boot 应用测试说明](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html)

**验收：** 测试失败时能看到哪条业务规则破坏；至少一次回滚测试验证真实数据库；测试连续执行两遍都通过；测试后开发库内容未变。回滚故障注入只在测试配置生效，不能留下公开的“模拟失败”业务接口。

**卡住时：** 全部 403，先分别检查登录与 CSRF；测试绿但页面错，检查是否把真实权限组件全替换成了 mock；第二次失败，检查测试数据是否独立；测试一直等，检查并发放行条件、连接池数量和等待超时。

Linux 常用操作先掌握 `pwd`、`ls`、`cd`、`cat`、`tail -n 100`、`ps`、`ss -ltnp`。读日志时先定位最新异常与 `Caused by`，再关联时间、请求和数据库情况。只处理自己项目的进程，不能见到 Java 就全部终止。前台启动适合初次排错；稳定运行与服务管理可以以后再深入。

Docker 的镜像是启动模板，容器是运行实例，数据库持久化卷承载容器外的数据。Compose 里应用访问数据库通常使用服务名，如 `db:3306`；容器内 `localhost` 指当前容器。宿主机访问数据库则使用实际映射端口。先学 `docker compose config`、`up -d`、`ps`、`logs`、`stop`，不把 `down -v` 当重启命令；`-v` 会删除相关卷。[Docker Compose down 文档](https://docs.docker.com/reference/cli/docker/compose/down/)

不安装 Docker 也可以通过本周核心验收：本机独立 MySQL、可执行 jar、外部配置、查看日志、备份恢复、另一个空目录按说明启动。把尚未练习的 Linux 或容器技能在学习记录中标为待完成。开发与学习工具的下载、许可和可用条件以使用时为准；A阶段不要求订阅AI或购买云资源；B真实模型调用另核对可用端点和预算。

备份示例先在项目根目录创建 `backups` 文件夹，将 `your_backup_user` 换成自己有相应权限的账号。`-p` 后不写密码，让客户端交互提示；文件名使用当天日期。

```powershell
mysqldump -u your_backup_user -p --single-transaction --no-tablespaces --set-gtid-purged=OFF --result-file=backups/ops_ticket_dev_20270201.sql ops_ticket_dev
```

这里不加 `--databases`，便于恢复到不同名称的空库。`--single-transaction` 面向本项目 InnoDB 表；备份时不要执行建表、改表等 DDL。Windows 使用 `--result-file` 可避免 PowerShell 重定向编码带来的问题。[MySQL 备份文档](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)

恢复完整步骤在自测答案中：先核对备份内容，再建立新空库，导入，核对数据并用临时配置启动。不能在尚未确认库名时执行清表、删库或覆盖导入。

**验收：** 备份文件存在且非空；恢复库包含当前版本已实现的表（首版用户、设备、工单、操作记录）；必要关联和数量正确；中文没有乱码；恢复库能支撑一次查询演示。只得到一个 `.sql` 文件还没通过恢复验收。

## 第18单元（原日期参考） 2月8日至14日 查询性能与线程池

**目标：做一次有证据的小优化，理解资源为什么有限。** 春节与学校安排可以挪动本周，先做索引实验；线程池或 JVM 内容可以使用第 19 周补齐。

| 本周任务 | 小时 | 做完留下什么 |
| --- | ---: | --- |
| 在测试库生成合理分布的几千条虚构工单，写出一个实际列表查询 | 3 | 数据数量、分布和查询条件 |
| 保存 EXPLAIN，设计一个候选联合索引，在相同条件下前后比较 | 5 | 执行计划与测量记录 |
| 写有界线程池小实验，观察队列、拒绝、异常与关闭 | 4 | 独立实验代码和现象解释 |
| 认识 JVM 堆、线程栈、GC，观察一次本机 Java 进程 | 3 | 一页概念与实际观察记录 |
| 独立解释优化取舍，完成两道链表或栈题和自测 | 3 | 优化说明与答案 |

先优化真实存在的列表查询，如报修人查看自己的某种状态工单。下面只是候选设计，是否有效由数据分布和实际执行计划决定，不要求 MySQL 必须选择它。

```sql
EXPLAIN
SELECT id, title, status, created_at
FROM ticket
WHERE reporter_id = 1 AND status = 'OPEN'
ORDER BY created_at DESC, id DESC
LIMIT 20;

CREATE INDEX idx_ticket_reporter_status_time
ON ticket (reporter_id, status, created_at DESC, id DESC);
```

索引能缩小定位范围或帮助排序，但会增加空间与写入维护成本。不能给每个字段都加一个索引就称作优化。阅读 `key`、`rows`、`Extra`；传统 EXPLAIN 的行数是估计，支持的 SELECT 可以用 `EXPLAIN ANALYZE` 看真实执行情况，它会实际执行查询。[MySQL EXPLAIN 文档](https://dev.mysql.com/doc/refman/8.4/en/using-explain.html)

固定数据量、过滤条件、机器和应用版本，先预热，再重复测量，例如各测 10 次，保留中位数和执行计划。只有几十行或耗时接近计时噪声时，如实写“差异不足以判断”，不要生成一个漂亮百分比。不要把 SQL 客户端耗时直接当成整个接口响应时间。

线程池实验使用 `corePoolSize=2`、`maximumPoolSize=2`、容量为 2 的 `ArrayBlockingQueue` 和 `AbortPolicy`。让前两项任务在门闩等待，再提交另外三项，观察第五项被拒绝；最后释放门闩、等待结果并关闭池。池限制正在执行的任务，队列限制等待任务；任务异常也要通过结果或日志观察。[Java 21 ThreadPoolExecutor](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)

JVM 本周只要求分清：对象通常占用堆；线程执行方法需要自己的栈帧；GC 回收不可达对象，并不保证数据库连接等外部资源被及时关闭。可以用 `jcmd -l` 找到自己的 Java 进程，再按 JDK 帮助检查堆信息。不要为了练习故意把个人电脑内存耗尽。

**验收：** 一条 SQL 优化有前后证据与局限；能解释线程池拒绝为何发生；实验退出后没有挂住的工作线程；能说出增加索引、线程数、堆大小各自不能解决的至少一个问题。

**自测：** 18.1 EXPLAIN 显示使用了索引，就能断言查询一定更快吗？18.2 两线程、两队列的池，在任务都不结束时连续提交五项会怎样？18.3 反复创建线程或把所有查询结果永久存到 List，会分别带来什么风险？

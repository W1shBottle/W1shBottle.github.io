## 项目要做成什么样

在现有 Java 工单系统上做一个**设备报修分诊助手**。管理员收到一张报修单，Python Agent 帮他查设备资料，给出处理建议、依据和需要追问的内容。管理员查看建议后决定如何处置。

例如工单 101 写着“打印机换过纸后仍提示缺纸”。助手先查这张单，拿到型号，再去设备手册找对应段落。查到依据就给排查步骤并标注出处。只写“打印机坏了”时先问型号和报错。需要派给谁、能否派单，由管理员和 Java 的权限、状态规则决定。

第一版用虚构数据交付“查单 → 检索 → 建议或追问”的单 Agent 演示。第二版在工单详情保存人工采纳或驳回的理由。关单后，只有经确认有效、适用设备清楚的处置经验才进入可检索案例。文章里的待处理和已关单双链路，在这里分别解决“这单怎么处理”和“哪些经验值得下次复用”。

设计参考来自黑马的智能工单案例。[课程文章](https://mp.weixin.qq.com/s/QuWxhz8wfpK-sziTApnKlg)

## 接下来的六个学习单元

每个单元交付一个可以单独演示的结果。能自己改一个输入、解释输出时，再往后走。

| 单元 | 动手任务 | 怎么知道做对了 |
| --- | --- | --- |
| 1 · 恢复 Python 手感 | 编三张工单，每张写编号、设备、状态、故障描述。用列表、字典和函数实现 `find_ticket(ticket_id)` | 传 101 找到原记录，传 999 得到空结果，传字符串得到参数错误。再换一张工单独立重跑 |
| 2 · 分诊建议的样子 | 用一张假工单调一次模型。用 Python 校验故障类别、建议、待补信息、依据编号和是否转人工 | “设备坏了”应追问型号或现象。缺字段或返回未知类别时，程序能解释失败。模拟和真调用分别记录 |
| 3 · 让模型查工单 | 把第一步的函数注册为只读工具。让模型根据用户问题选工具，Python 执行并把结果交回模型 | 保存一次完整调用记录。用不存在的编号再试一次，回答应明确查无工单 |
| 4 · 给建议找依据 | 加资料检索工具。先搜维修手册和已确认解决的历史工单，按设备型号、版本筛选。把本次报修人的补充描述作为查询线索 | 为一张报修单标出支持建议的资料编号和段落，再用型号不匹配的资料验证会追问或转人工 |
| 5 · 让执行过程可查 | 用普通 Python 包住工具调用循环，校验工具参数，限制步数和超时，记录每步的工具、结果和结束原因。这一层就是本项目的 Agent Harness | 让工具超时一次，再让模型重复请求同一工具。两次任务都应在边界内结束，并给管理员留下可读的原因 |
| 6 · 把建议交给人 | 在隔离工单详情展示建议和证据，先允许人工采纳或驳回。需要真实派单时，由已授权管理员通过 Java 接口提交 | 演示采纳、驳回两条路径。同一建议重复提交只产生一次操作，旧版本建议不能覆盖新的工单状态 |

## B/G：先做可运行的小Agent

1. Python内存里构造假工单，写 `find_ticket(ticket_id)` 和 `list_tickets(status)`，正常、无数据、非法参数均能处理。
2. 调用一个模型API：先让它理解用户问题并输出摘要，再让它实际请求一个工具；由Python按工具名/参数调用函数，把结果送回模型。
3. 加入有限步数、超时、失败提示和过程记录。先做一个Agent、一两个只读工具；LangChain可辅助模型/工具集成，LangGraph在确需多步状态时引入。
4. 对话歧义时追问，能展示实际工具调用记录和任务结果。模型输出不是数据库事实，也不自动获得业务权限。

先用假数据不要求真实用户登录；这只是学习原型，不宣传为有权限的业务系统。模型服务能看到发送给它的内容，因此只用虚构样本，key从环境变量获取，不写入代码或日志。

## 与Java联调和权限边界

Python先调用本机、隔离数据上的只读接口，记录HTTP状态、超时及错误，不先做写入。真实多用户场景必须先有Java认证和资源归属校验，以及服务间身份传递；服务端从可信会话或明确设计的服务凭据取得身份，不能信任模型生成的userId。认证缺失时只做假数据实验，不对公网开放开发接口。

需要时再由Java请求Python提供的Agent接口；两个进程带来启动、配置、依赖版本、超时、日志和联调成本，先分别调通，再连接。工具禁止模型拼任意SQL、执行系统命令或任意URL；写工具留到人工确认、重新鉴权、状态和幂等均能验证后。

## 知识检索与评测

准备10—20条自编虚构维护资料，记录资料ID、版本、设备范围、段落。先做关键词检索并给出处，语义效果不足时再试Embedding与向量库；查无依据就说明不足。资料本身不授予权限。

从约12—20条正常、模糊、无结果和错误输入开始，逐步扩展约30条Agent任务，区分开发集与留出集。分别记录检索命中、工具选择和参数、任务完成、引用依据、失败原因、延迟和真实用量/费用；缺费用写未知。先定判断标准，再比较修改前后，不能只保留成功截图。

### 什么时候引入文章里的进阶技术

- **Skill 和 LangGraph。** 当同一排查流程已在多个案例中复用，可把“打印机缺纸”写成一份带版本的操作指南（SOP），只在型号匹配时加载。拿同一批案例比较改 SOP 前后的引用与转人工结果。出现等待补充、恢复执行等状态后，再考虑用 LangGraph 表达分支。
- **异步与 Redis。** 当模型响应拖慢建单，再把分析改成后台任务。每次变更有独立事件 ID 和工单版本，分别试同一事件重放、同一工单连续两次更新、旧结果晚到。Redis 可辅助短时去重，持久化唯一约束和版本检查保证回写正确。Kafka 留到需要独立消费和重放时再接。
- **检索优化。** 固定一组问题先测关键词检索。相同故障换说法就漏查，再对比向量召回。候选里有正确资料却排得太低，再试重排序。记录正确引用数、总题数和一个失败样本。跨设备多跳关联成为真实问题时，再试 Neo4j / GraphRAG。
- **微调与本地推理。** SFT、LoRA、DPO 和 vLLM 留作远期选修。先积累人工确认的案例和采纳记录，分清是检索、工具还是模型判断出错，再判断是否值得训练或部署自己的模型。

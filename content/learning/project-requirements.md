## 1. 项目背景与目标用户

以园区或实验室的设备故障为场景：报修人提交故障，管理员派给工程师，工程师处理后交给报修人验收。使用模拟数据，不接入真实硬件。

| 后续 Web 角色 | 计划权限 |
| --- | --- |
| 报修人 REPORTER | 提交工单、查看自己的工单、验收通过（评论与驳回延后） |
| 工程师 ENGINEER | 查看分给自己的工单、提交处理结果 |
| 管理员 ADMIN | 查看工单、派单（首版设备使用初始化数据） |

Java 当前没有用户实体、登录或权限检查；SQL 已有 app_user 表，不能据此认定已实现认证。`assign` 接受正整数工程师编号，不会验证这个人是否存在或具有工程师角色。

## 3. 状态规则

| 操作 | 前置状态 | 成功后 | 实现状态 |
| --- | --- | --- | --- |
| 创建 | 无 | OPEN | 已实现 |
| 派单 | OPEN | IN_PROGRESS | 已实现 |
| 提交处理结果 | IN_PROGRESS | RESOLVED | 待实现 |
| 验收通过 | RESOLVED | CLOSED | 待实现 |
| 验收驳回 | RESOLVED | IN_PROGRESS | 延后，首版不做 |

`RESOLVED`、`CLOSED` 已定义，恢复入口可以重建这两种状态，但相应的业务流转方法尚未实现。`rename` 当前仅校验标题，完整的关闭后变更限制尚未实现。后续通过有业务含义的方法流转状态，再引入操作者权限和日志。

## 4. 仓库接口约定

| 方法 | 约定 | 实现与验证范围 |
| --- | --- | --- |
| add | 拒绝 null、重复编号；不得覆盖原记录 | 两种实现通过内存仓库执行校验；内存新增、重复和 null 已有 JUnit |
| findById | 存在返回包含对象的 Optional，不存在返回空 Optional | 内存已有 JUnit；Service 用 orElse(null) 保留原调用约定 |
| findAll | 返回按插入顺序排列的新列表 | 内存列表结构隔离已有 JUnit；元素仍共享引用，修改后需显式 update |
| update | 仅替换已有编号；拒绝 null 和不存在编号 | 内存成功替换、未知编号拒绝已有 JUnit；update(null) 作为已理解的同类练习跳过，未计入测试 |

FileTicketRepository 查询复用内部内存仓库，新增/更新后保存文件。构造器只在缺文件时以空仓库继续，其他 IOException 向外抛出，内容错误以 IllegalArgumentException 抛出。保存时 IOException 包装为 UncheckedIOException；ConsoleApp 提示并退出。

文件写入失败不保证内存回滚，不能把这一实现解释成事务仓库。共用流程 Demo 已验证两种实现创建、查询、改标题和派单的结果一致，并验证新文件仓库恢复；这不代表所有仓库契约都有双实现自动测试。

## 6. 第一版最小功能范围（计划，尚未实现）

一条闭环：**报修人创建 → 管理员派单 → 指定工程师提交处理说明 → 原报修人验收关闭**。主状态仍是 OPEN→IN_PROGRESS→RESOLVED→CLOSED。

- 三角色固定，种子用户/设备；无公开注册、复杂组织、设备维护后台。
- 创建绑定启用设备，身份来自会话；标题、描述分别校验；不能冒充报修人。
- 详情/列表按当前用户可见范围查询；支持必要的标题、状态筛选及有限分页。
- 派单检查管理员身份、工程师存在/角色/启用状态、OPEN 和期望版本。
- 处理说明非空且有长度上限，只能由该工单当前工程师提交；验收只能由原报修人执行。
- 状态变更与必要操作日志同事务；仅合法迁移，CLOSED 不再变更。
- 必要登录、参数错误、无权访问、不存在、重复请求和版本冲突均有可解释的响应。
- 先通过接口工具演示；可随后增加登录、列表/创建、详情/操作三个简洁页面，不要求学习大型前端框架才接 AI。

最小表结构为现有 app_user、device、ticket，随后增加 **ticket_action_log**。处理说明存 resolve 操作记录的 note，详情读取操作记录；暂不新增 ticket_comment 或 ticket_resolution。现有 SQL 不在本次重建或自动执行。

创建用 requestKey 防止重复提交：同一用户、同一动作、同一个 key 的相同输入返回原 ticketId；不同输入返回 409。存请求摘要用于比较，不以“标题相同”判重。并发重复日志唯一约束冲突必须回滚本次新工单，再查已完成操作。其他状态操作先以 expectedVersion＋前置状态条件更新；重复/竞争失败返回 409、不新增重复日志。具体设计见 design.md 第 10 节。

## 7. 三阶段计划与验收

| 阶段 | 学习与交付 | 必须能证明 |
| --- | --- | --- |
| A1 Java 后端业务 | 读已有 Ticket/Service/SQL；短 JDBC 后逐步接 Boot/MyBatis；完成核心闭环 | 能画出 Controller→Service→Mapper→MySQL；独立增加一个查询条件；新建/派单/解决/验收真实落库；能解释表关系和状态规则 |
| A2 基础工程 | Session＋Spring Security、角色与归属、输入校验、统一错误、事务日志、版本冲突、关键测试、最小部署 | 未登录、越权、错误工程师、非法迁移、同 key 重试、并发派单有结果证据；日志失败时状态一起回滚；另一环境可运行并能读日志定位故障 |
| B 一个 AI 功能 | 模型 API→结构化工单摘要/分类/补充信息建议→用户确认采纳 | 至少一次真实模型验证；超时、HTTP 错误、无效 JSON、拒答均可恢复；AI 关闭后 A 所有业务正常；无后台自动改状态 |
| C 验证与改进 | 固定数据集、无 AI 基线、失败归因、提示/解析调整、留出案例复验 | 报告样本数、合法率、内容忠实度/可用性、用量、延迟与成本；能说明实际改善和限制，不伪造指标 |

A1/A2 完成即可进入 B，不等 Redis/消息队列/微服务。C 不以固定周数承诺效果，评估从首次真实调用就开始。Agent 仅在现有功能表现可靠且有自然语言查询需求后加入；第二项目等能力缺口明确后再决定。

## 9. AI 与可选 Agent 路线（计划）

首个功能是对**有权访问的既有工单**生成 `{summary, category, missingInformation}`。category 只允许 DISPLAY/PRINTING/HVAC/OTHER/UNKNOWN，模型只给建议，分类不自动作为工单字段落库。输入不足时明确 UNKNOWN/待补充信息，不臆造设备型号、维修步骤或已完成处理。首版仅展示/复制参考，不提供直接回写按钮，原始描述保留。现有 rename 只在控制台/Service 中，不是 HTTP 接口。以后如需人工采纳改标题，再定义报修人归属、允许状态、expectedVersion 和操作日志同事务的接口后实现。

先用 Java ModelClient 边界调用选定模型 API，供应商/模型/密钥/费用上限到 B 前配置；没有密钥时可做解析器的模拟测试，但标记“真实模型未验证”。超时、429/5xx、格式错误和模型拒答区分记录；单次限时、有限重试、用户级配额，不开无限重试。网络请求在数据库写事务之外；关闭 AI 不影响工单读写。

- **RAG 可选**：只有需要设备手册依据的问答时才做。记录资料来源/许可、版本、切片和导入结果；按用户可见范围检索，返回可定位引用。检索无依据时明确无法给出基于资料的回答；把检索召回与生成错误分别评估，不凭模型编造出处。
- **只读工具 Agent 可选**：先两个受控工具查本人/授权范围工单、读工单详情；工具复用 Service，每次重验权限、参数和返回字段。模型不能执行任意 SQL、文件命令或任意 URL。只有简单调用稳定后再给有限步数/次数/时长，处理超时、工具错误和对话上下文过期；每步保留可审查结果。
- **写工具更后置**：不把模型建议当授权。确认页面展示操作对象、字段和版本；用户确认绑定具体动作，再由服务重新做权限/状态/版本/参数检查，拒绝过期确认。给模型的资料或对话不能提升权限。

AI 辅助编码单独训练：每个模块允许助手解释/评审，学习者必须追踪调用链、独立改一处需求、设计一个有意义的失败场景并定位修复；记录哪些代码由谁写。上述练习不等于产品已经实现 AI。

## 1. 项目背景与目标用户

以园区或实验室的设备故障为场景：报修人提交故障，管理员派给工程师，工程师处理后交给报修人验收。使用模拟数据，不接入真实硬件。

| 后续 Web 角色 | 计划权限 |
| --- | --- |
| 报修人 REPORTER | 提交工单、查看自己的工单、评论、验收通过或驳回 |
| 工程师 ENGINEER | 查看分给自己的工单、评论、提交处理结果 |
| 管理员 ADMIN | 管理设备、查看工单、派单 |

当前没有用户实体、登录或权限检查。`assign` 接受正整数工程师编号，不会验证这个人是否存在或具有工程师角色。

## 4. 仓库接口约定

| 方法 | 约定 | 实现与验证范围 |
| --- | --- | --- |
| add | 拒绝 null、重复编号；不得覆盖原记录 | 两种实现通过内存仓库执行校验；内存新增、重复和 null 已有 JUnit |
| findById | 存在返回包含对象的 Optional，不存在返回空 Optional | 内存已有 JUnit；Service 用 orElse(null) 保留原调用约定 |
| findAll | 返回按插入顺序排列的新列表 | 内存列表结构隔离已有 JUnit；元素仍共享引用，修改后需显式 update |
| update | 仅替换已有编号；拒绝 null 和不存在编号 | 内存成功替换、未知编号拒绝已有 JUnit；update(null) 作为已理解的同类练习跳过，未计入测试 |

FileTicketRepository 查询复用内部内存仓库，新增/更新后保存文件。构造器只在缺文件时以空仓库继续，其他 IOException 向外抛出，内容错误以 IllegalArgumentException 抛出。保存时 IOException 包装为 UncheckedIOException；ConsoleApp 提示并退出。

文件写入失败不保证内存回滚，不能把这一实现解释成事务仓库。共用流程 Demo 已验证两种实现创建、查询、改标题和派单的结果一致，并验证新文件仓库恢复；这不代表所有仓库契约都有双实现自动测试。

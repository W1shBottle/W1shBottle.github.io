核对日期：2026-10-17（凌晨）。本次学习归 2026-10-16。当前：v0.1 开发中。

## 1. 项目背景

以园区或实验室的设备故障为场景：报修人提交故障，管理员派给工程师，工程师处理后交给报修人验收。使用模拟数据，不接入真实硬件。

最终希望能够追踪“谁提交了问题、谁负责处理、当前处理到哪一步、为什么发生状态变化”。

## 2. 目标用户（后续 Web 阶段）

| 角色 | 计划权限 |
| --- | --- |
| 报修人 REPORTER | 提交工单、查看自己的工单、评论、验收通过或驳回 |
| 工程师 ENGINEER | 查看分给自己的工单、评论、提交处理结果 |
| 管理员 ADMIN | 管理设备、查看工单、派单 |

当前没有用户实体、登录或权限检查。assign 接受正整数工程师编号，不会验证这个人是否存在或具有工程师角色。

## 4. 状态规则

| 操作 | 前置状态 | 成功后的状态 | 实现状态 |
| --- | --- | --- | --- |
| 创建 | 无 | OPEN | 已实现 |
| 派单 | OPEN | IN_PROGRESS | 已实现 |
| 提交处理结果 | IN_PROGRESS | RESOLVED | 待实现 |
| 验收通过 | RESOLVED | CLOSED | 待实现 |
| 验收驳回 | RESOLVED | IN_PROGRESS | 待实现 |

RESOLVED、CLOSED 已定义为枚举值，恢复入口可以重建这两种状态，但相应的业务流转方法尚未实现。后续关闭后的工单不再进行业务变更；当前 rename 只有标题校验，完整的关闭限制尚未实现。

业务状态通过具有明确含义的方法修改，避免开放任意 setStatus 绕过规则。后续 Web 阶段再检查操作者权限，并记录操作日志。

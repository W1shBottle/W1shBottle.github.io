## 1. 项目背景与目标用户

以园区或实验室的设备故障为场景：报修人提交故障，管理员派给工程师，工程师处理后交给报修人验收。使用模拟数据，不接入真实硬件。

| 后续 Web 角色 | 计划权限 |
| --- | --- |
| 报修人 REPORTER | 提交工单、查看自己的工单、评论、验收通过或驳回 |
| 工程师 ENGINEER | 查看分给自己的工单、评论、提交处理结果 |
| 管理员 ADMIN | 管理设备、查看工单、派单 |

当前没有用户实体、登录或权限检查。`assign` 接受正整数工程师编号，不会验证这个人是否存在或具有工程师角色。

| --- | --- | --- |

标题长度按 Java `String.length()` 的 UTF-16 代码单元计数，不按用户感知字符数计数。自动编号当前面向单线程内存练习，不提供数据库自增或并发编号分配。

## 3. 状态规则

| 操作 | 前置状态 | 成功后 | 实现状态 |
| --- | --- | --- | --- |
| 创建 | 无 | OPEN | 已实现 |
| 派单 | OPEN | IN_PROGRESS | 已实现 |
| 提交处理结果 | IN_PROGRESS | RESOLVED | 待实现 |
| 验收通过 | RESOLVED | CLOSED | 待实现 |
| 验收驳回 | RESOLVED | IN_PROGRESS | 待实现 |

`RESOLVED`、`CLOSED` 已定义，恢复入口可以重建这两种状态，但相应的业务流转方法尚未实现。`rename` 当前仅校验标题，完整的关闭后变更限制尚未实现。后续通过有业务含义的方法流转状态，再引入操作者权限和日志。

`TicketService` 与 `InMemoryTicketRepository` 暂时独立。文件存储类也尚未实现 `TicketRepository`，不能把接口练习描述成已完成可切换存储。

## 6. 下一步任务

1. 补仓库的重复新增、null、更新存在/不存在编号、返回列表结构隔离等 JUnit；失败后检查数据没有被错误修改。
2. 在行为明确后，让 Service 通过 TicketRepository 操作存储，迁移现有功能并保持已验证的行为；处理 Service 的 null 与 Repository 的 Optional 返回约定。
3. 随课程继续按职责拆分，再安排其他存储实现；文件坏数据测试逐步纳入自动测试，不一次性宣布覆盖全部异常。

文件写入中途失败的原子替换、备份保护仍待实现。当前坏存档保护验收只证明读取/启动失败时没有写回原档，不等于写入失败也安全。不纳入当前阶段：微服务、Kubernetes、支付、真实设备通信。
